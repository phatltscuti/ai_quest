2. Yêu cầu 2: Cài đặt Google Workspace CLI và MCP server trên môi trường của tôi

Phần này ghi lại quá trình cài đặt đúng như tôi đã làm. Thứ tự theo hướng dẫn chính thức: cài binary, tạo OAuth client gắn cờ agent trong một Google Cloud project, đăng nhập CLI, rồi kết nối một MCP client với các server remote dùng chung project đó.

2.2 Bước 1: Cài gwscli trên Windows

Hướng dẫn có sẵn một lệnh PowerShell một dòng tải install.ps1 về rồi chạy bằng iex. Cách đó chạy được, nhưng trên laptop công ty tôi không thích pipe một script từ xa thẳng vào shell, nên tôi chọn cách thủ công: tải binary duy nhất bằng curl.exe, đặt vào một thư mục có trong PATH và kiểm tra version. Lưu ý phải gọi tường minh curl.exe: trong Windows PowerShell, curl chỉ là alias của Invoke-WebRequest và nhận tham số khác.

New-Item -ItemType Directory -Force "$HOME\bin" | Out-Null
curl.exe -fL -o "$HOME\bin\gwscli.exe" https://dl.google.com/workspace-cli/windows/gwscli.exe

# thêm $HOME\bin vào user PATH (một lần), rồi mở terminal mới
[Environment]::SetEnvironmentVariable("Path", [Environment]::GetEnvironmentVariable("Path","User") + ";$HOME\bin", "User")

gwscli version
gwscli version 1.0.6.1026726559

Ngay ở bước này đã có hai nhận xét. Thứ nhất, chuỗi version này là thông tin version duy nhất tôi tìm được: trang release notes chỉ có một mục ghi ngày (24/11/2026) và không có số version, nên không có cách nào đối chiếu "1.0.6.1026726559" với changelog. Thứ hai, không có lệnh tự cập nhật. Muốn nâng cấp thì tải lại binary, và vì agent skills nằm trong binary nên sau đó phải cài lại skills (xem 3.3).

2.3 Bước 2: Project personal mode và OAuth client gắn cờ agent

Với một developer, đường nhanh nhất là personal mode. Hướng dẫn CLI dẫn tới một trang Cloud console (auth/overview/personal với tham số apis=ws,wsmcp,tasksmcp, clientType=desktop và isAgent=true). Chỉ trong một form, trang này tạo project mới, bật các Workspace API cùng phần MCP đi kèm, và tạo một OAuth client chỉ hoạt động với tài khoản của tôi, nên không cần cấu hình consent screen hay app verification.

Tôi điền tên project ai-quest-gwscli-demo, chọn application type Desktop app, đặt tên client là gwscli-mcp-agent và tick Use this client for an AI-powered agent. Checkbox này là phần quan trọng: theo trang troubleshooting của cả CLI và MCP, request user-delegated đến từ client không có cờ này sẽ bị các endpoint agent của Workspace từ chối.

Sau khi bấm Continue, console tạo project, bật các Workspace API cùng các MCP API đi kèm, và hiển thị client mới đúng một lần kèm nút Download JSON. Sau khi đóng hộp thoại thì không xem lại được secret nữa, nên tôi lưu file JSON thẳng vào một thư mục đã được git-ignore.

Personal mode rất hợp cho một bài test như thế này, nhưng nó bị giới hạn có chủ đích: client chỉ hoạt động với Google Account đã tạo ra nó. Với một team, nên dùng cài đặt thủ công (bật từng API và phần *mcp đi kèm, cấu hình consent screen, mỗi agent một client) và tốt nhất là để Workspace admin rà soát.

2.4 Bước 3: Đăng ký client và đăng nhập CLI (cấp scope theo từng phần)

CLI lưu hai thứ ở máy local: OAuth client đã đăng ký (từ gwscli auth setup) và grant của người dùng kèm refresh token (từ gwscli auth login). Trên Windows cả hai nằm trong %AppData%\gwscli (client_credentials.json và token.json). Thay vì dùng bundle chỉ đọc, tôi chỉ xin đúng những gì kịch bản cần: các service Drive, Calendar và Tasks cùng một action Gmail duy nhất là create_draft.

PS> echo Y | gwscli auth setup --oauth_client_file=client_secret.json
Configuring your OAuth Client will first remove your existing stored OAuth tokens (logout), are you sure you want to proceed? Y, N.
Already logged out (no cached token found).
Successfully configured OAuth client credentials (client_id: ****).

PS> gwscli auth login drive calendar tasks "gmail create_draft"
Please open the following URL in your browser to log in:
[Open this URL in your browser to sign in]
Waiting for authorization code on localhost:61118...
Successfully authorized the following scopes:
  - https://www.googleapis.com/auth/calendar
  - https://www.googleapis.com/auth/calendar.events.readonly
  - https://www.googleapis.com/auth/calendar.readonly
  - https://www.googleapis.com/auth/drive.file
  - https://www.googleapis.com/auth/drive.metadata.readonly
  - https://www.googleapis.com/auth/drive.readonly
  - https://www.googleapis.com/auth/gmail.compose
  - https://www.googleapis.com/auth/tasks

Toàn bộ quá trình đăng nhập mất khoảng 37 giây, tính cả bước consent trên trình duyệt. Có ba điều tôi để ý:

  • "Service" nghĩa là scope rộng. Xin service calendar sẽ được cấp scope đầy đủ https://www.googleapis.com/auth/calendar, mà màn hình consent mô tả là "See, edit, share, and permanently delete all the calendars you can access". Nếu chỉ cần một action, hãy ghi rõ action đó (ví dụ "calendar list_events") thay vì cả service.
  • gmail.compose không chỉ là bản nháp. Tôi chỉ xin create_draft, nhưng màn hình consent ghi "Manage drafts and send emails". CLI không có lệnh gửi, nhưng bản thân token vẫn cho phép gửi mail nếu bị lộ. Đây chính là lý do file token phải được coi như secret.
  • Agent không thể tự điều khiển bước đăng nhập. CLI in ra một URL và chờ trên một cổng localhost ngẫu nhiên; con người phải hoàn tất consent trên trình duyệt ở cùng máy. Trong demo, tôi mở URL đó trong một Chrome profile riêng.

2.5 Bước 4: Các MCP server remote: kiểm tra giao thức và đăng ký vào Claude Code

Các MCP server là endpoint do Google host, nên "cài đặt" chúng nghĩa là trỏ một MCP client tới URL kèm OAuth token lấy từ một client có gắn cờ agent. Tôi kiểm tra chúng theo hai cách.

(a) Một MCP client thô. Để quan sát giao thức mà không có agent nào xen vào giữa, tôi viết một script Python khoảng 60 dòng (mcp_probe.py) nói chuyện MCP qua Streamable HTTP: nó gửi initialize, tools/list và tuỳ chọn tools/call dưới dạng JSON-RPC, dùng access token mà gwscli đã lấy được (token được đọc từ cache và không bao giờ in ra). Đây là output thật khi chạy với các server Drive, Calendar và Tasks:

> POST https://drivemcp.googleapis.com/mcp/v1  initialize
  HTTP 200 in 495 ms  server={"name": "StatelessServer", "version": "ESF"}  protocol=2025-06-18
> tools/list
  HTTP 200 in 496 ms  9 tools:
   - copy_file                    [write]
   - create_file                  [write]
   - download_file_content        [read-only]
   - get_file_metadata            [read-only]
   - get_file_permissions         [read-only]
   - list_recent_files            [read-only]
   - read_file_content            [read-only]
   - search_files                 [read-only]
   - upload_file_revision         [DESTRUCTIVE]

> POST https://calendarmcp.googleapis.com/mcp/v1  initialize
  HTTP 200 in 477 ms  9 tools: list_events, get_event, list_calendars, suggest_time [read-only],
  create_event, update_event, respond_to_event [write], delete_event [DESTRUCTIVE], search_events [read-only]

> POST https://tasksmcp.googleapis.com/mcp/v1  initialize
  HTTP 200 in 915 ms  9 tools: list_task_lists, list_tasks, get_task [read-only],
  create_task, update_task, undelete_task, complete_task, uncomplete_task [write], delete_task [DESTRUCTIVE]

Những điều hữu ích rút ra từ bước kiểm tra này: các server là stateless (serverInfo "StatelessServer", không cần session id), dùng MCP protocol version 2025-06-18, một round trip từ Việt Nam mất khoảng 0,45–1 giây, và mọi tool đều mang MCP annotation (readOnlyHint / destructiveHint). Chính các annotation này được MCP client dùng để quyết định tool nào được chạy mà không cần hỏi. Danh sách tool khớp một-một với danh sách lệnh CLI của Drive, Calendar và Tasks, xác nhận rằng CLI chỉ là một client mỏng phía trên cùng một backend. Endpoint Tasks (tasksmcp.googleapis.com), vốn không có trong trang cấu hình MCP, thực ra vẫn tồn tại và phản hồi bình thường.

(b) Đăng ký server trong Claude Code. Claude Code chấp nhận MCP server HTTP remote với một OAuth client đã đăng ký sẵn. Secret được lấy từ biến môi trường MCP_CLIENT_SECRET (hoặc được hỏi khi chạy), nên không bao giờ xuất hiện trên dòng lệnh:

PS> claude mcp add --transport http gws-drive https://drivemcp.googleapis.com/mcp/v1 --client-id **** --client-secret --callback-port 8765
Added HTTP MCP server gws-drive with URL: https://drivemcp.googleapis.com/mcp/v1 to local config

PS> claude mcp list
Checking MCP server health...
gws-drive: https://drivemcp.googleapis.com/mcp/v1 (HTTP) - Connected

Client loại Desktop chấp nhận redirect URI loopback trên bất kỳ cổng nào, nên cổng callback cố định 8765 hoạt động mà không cần đăng ký redirect URI trong console. Sau đó, bước OAuth consent của người dùng cho server được hoàn tất ngay trong Claude Code bằng /mcp.

3. Yêu cầu 3: Tác vụ thực tế với CLI và agent kết nối MCP

Để thử công cụ trên thứ gì đó gần với công việc thật, tôi dùng một kịch bản nhỏ mà tuần nào tôi cũng làm: chuẩn bị báo cáo tuần, lưu lại, lên lịch review, theo dõi việc cần làm tiếp và nhờ đồng nghiệp review. Báo cáo là một file demo ngắn tôi tự viết cho bài này. Kịch bản chạm tới năm dịch vụ (Drive, Calendar, Tasks, Gmail, và Drive lần nữa để đọc), kết hợp thao tác đọc và ghi, và có một thao tác cần con người quyết định.

Upload báo cáo (Drive)→ Tìm + đọc lại→ Họp review (Calendar)→ Việc cần làm (Tasks)→ Nháp email (Gmail, HITL)

3.1 Khám phá lệnh lúc chạy

Vì CLI không cam kết chữ ký lệnh ổn định, việc đầu tiên tôi (và sau này là agent) làm là hỏi chính binary: --help để xem flag, --schema để xem output JSON và --show-scopes để xem scope tối thiểu của một action. Ví dụ:

PS> gwscli drive create_file --help --show-scopes
OAuth Scopes:
  All Supported Scopes:
    - https://www.googleapis.com/auth/drive
    - https://www.googleapis.com/auth/drive.appdata
    - https://www.googleapis.com/auth/drive.file
  Recommended Minimal Scopes:
    - https://www.googleapis.com/auth/drive.file

Các đoạn help được viết cho model chứ không phải cho con người: create_event giải thích rằng thời gian phải truyền vào không kèm UTC offset trừ khi người dùng nêu rõ, create_task chứa cả một bộ quy tắc về deadline so với ngày lên lịch và phải nói gì với người dùng khi bỏ deadline, còn search_files mô tả toàn bộ ngữ pháp truy vấn. Nói cách khác, phần "prompt engineering" cho từng tool được đóng gói sẵn trong binary.

3.2 Tác vụ thực tế với CLI: chuyện gì đã thực sự xảy ra

Tôi chạy kịch bản đã lên kế hoạch (upload một báo cáo tuần hư cấu, tìm lại nó, lên lịch buổi review, tạo task theo dõi, soạn nháp email) bằng các lệnh thật. Mọi lệnh đều tới được Google và nhận về câu trả lời có cấu trúc, nhưng không thao tác Workspace nào được phép chạy:

#Lệnh (rút gọn)Thời gianKết quả
1drive create_file --title "AIQuest gwscli demo - weekly report" --filePath data/aiquest-gwscli-demo-report.md --contentMimeType text/markdown1,4 sHTTP 403 PERMISSION_DENIED "The caller does not have permission" (ở bước khởi tạo upload)
2drive search_files --query "title contains 'AIQuest gwscli demo'" --excludeContentSnippets1,6 sisError: "The caller does not have permission"
3calendar create_event --summary "AIQuest demo: review gwscli report" --startTime 2026-11-26T10:00:00 --endTime 2026-11-26T10:30:001,2 sisError: project phải được ghi danh vào Developer Preview Program
4calendar list_events --fullText "AIQuest demo"1,5 scùng lỗi Developer Preview
5tasks create_task --title "AIQuest demo: send weekly report" --scheduledDate 2026-11-262,7 scùng lỗi Developer Preview
6gmail create_draft --to demo@example.com --subject "AIQuest demo: weekly report" --body "..."4,1 scùng lỗi Developer Preview

Thông báo chính xác cho Calendar, Tasks và Gmail là:

{
  "content": [
    {
      "text": "Access to this tool requires that your Google Cloud project (7728xxxxxxxx) is enrolled in the Google Workspace Developer Preview Program. Please see https://developers.google.com/workspace/preview",
      "type": "text"
    }
  ],
  "isError": true,
  "resultType": "complete"
}

Trước khi kết luận, tôi đã loại trừ các nguyên nhân hiển nhiên. Các API đã được bật: trang "Enabled APIs & services" của project liệt kê Drive, Calendar, Tasks, Gmail, Docs, Sheets, Slides, Chat và Workspace MCP API cùng các API cổ điển, và các MCP API của Drive/Calendar/Tasks đã ghi nhận request của tôi (kèm lỗi) trên biểu đồ traffic. Các scope đã được cấp (xem 2.4). Client có gắn cờ agent. Và nội dung lỗi rất rõ ràng: thứ chặn lại là việc project chưa được ghi danh vào Developer Preview Program, không phải token của tôi. Drive trả về thông báo chung chung kém hữu ích hơn là "caller does not have permission", nhưng nó thất bại ở cùng một giai đoạn, cả qua CLI lẫn qua MCP thô (bên dưới).

Cũng cần để ý định dạng output nói lên điều gì: kết quả của CLI đúng nghĩa đen là một MCP tool result (mảng content, isError, resultType). Điều này xác nhận những gì tài liệu ngụ ý: gwscli là một MCP client của chính các server do Google host, với giao diện dòng lệnh và khả năng xử lý file local. Không có câu hỏi xác nhận human-in-the-loop nào cho create_draft, vì request đã bị từ chối trước khi server đi tới bước đó.

3.3 Cùng các lần gọi đó qua MCP thô

Để chắc chắn vấn đề không nằm ở CLI, tôi thực hiện cùng loại lời gọi trực tiếp tới các MCP endpoint bằng mcp_probe.py. Handshake và tools/list thành công (mục 2.5), còn tools/call thất bại với đúng các thông báo đó:

> tools/call search_files {"query": "title contains 'AIQuest'"}
  HTTP 200 in 533 ms
  { "content": [ { "text": "The caller does not have permission", "type": "text" } ], "isError": true }

> tools/call list_calendars {}            (calendarmcp)
  HTTP 200 in 445 ms   "Access to this tool requires that your Google Cloud project (...) is enrolled in the Google Workspace Developer Preview Program."

> tools/call list_task_lists {}           (tasksmcp)
  HTTP 200 in 955 ms   same Developer Preview message

Có hai chi tiết giao thức đáng lưu ý cho ai đang viết MCP client: lỗi của tool trả về dưới dạng HTTP 200 với isError: true bên trong result, không phải HTTP error hay JSON-RPC error, nên client bắt buộc phải kiểm tra flag này; và bước discovery (initialize và tools/list) không bị chặn, chỉ có bước thực thi bị chặn. Nói cách khác, agent có thể thấy mọi tool, lên kế hoạch với chúng, và chỉ phát hiện ra lúc gọi rằng mình không được phép dùng.

3.4 Tác vụ cho agent: Claude Code với skill gwscli

CLI đi kèm agent skill riêng. Cài nó chỉ cần một lệnh, lệnh này ghi ra một file SKILL.md:

PS> gwscli skills install --dir .claude/skills
Installing skills to .claude/skills...
PS> tree /F .claude
\---skills
    \---gwscli
            SKILL.md

Sau đó tôi giao cho Claude Code một tác vụ bằng ngôn ngữ tự nhiên, không nêu tên lệnh, và chỉ cho phép nó chạy các lệnh gwscli (cộng với đọc file và dùng skill):

claude -p "Use the gwscli skill: find my Drive files whose title contains AIQuest, then list my Google Tasks lists. Report exactly what happened, including any error text. Do not try to change any settings." --allowedTools "Bash(gwscli:*)" Read Skill

Lần chạy mất 26 giây. Những gì agent đã làm (theo câu trả lời của nó, vốn bằng tiếng Việt do cài đặt global của tôi):

  1. Đầu tiên nó kiểm tra phiên bản CLI theo hướng dẫn của skill (skill yêu cầu tối thiểu version 0.2.0); bản local 1.0.6 của tôi đạt yêu cầu.
  2. Nó tự dựng đúng truy vấn có cấu trúc: gwscli drive search_files --query="title contains 'AIQuest'", và báo exit code 1 kèm "The caller does not have permission". Nó nói rõ đây là lỗi quyền truy cập, không phải "không có file nào khớp".
  3. Nó chạy gwscli tasks list_task_lists và trích nguyên văn thông báo Developer Preview, kể cả số project.
  4. Nó đề xuất bước tiếp theo cho tôi (ghi danh project, hoặc cấp lại quyền cho action Drive) và không thử thay đổi cài đặt nào, đúng như yêu cầu. Nó cũng nhận ra MCP server gws-drive có sẵn trong phiên và đề nghị thử theo hướng đó.

Vậy là dù backend bị đóng, bài test thực tế vẫn trả lời được câu hỏi "nó vận hành thế nào trong thực tế": skill cho agent đủ hướng dẫn để chọn đúng lệnh và cú pháp ngay lần đầu, các lỗi MCP có cấu trúc giúp agent dễ hiểu và báo cáo trung thực, và ranh giới quyền (chỉ được dùng gwscli, không đổi cài đặt) được tôn trọng. Khi project được ghi danh, cùng prompt đó sẽ trả về kết quả mà tôi không cần thay đổi gì.

Tình trạng các tác vụ ghi. Việc ghi danh vào Developer Preview Program là một yêu cầu do Google xét duyệt, nên không thể hoàn tất trong thời gian thực hiện bài test này. Các lệnh của kịch bản được giữ trong demo-assets/film_gws.py để có thể chạy lại y hệt sau khi được duyệt, và tôi sẽ cập nhật bài viết này với kết quả.

4. Yêu cầu 4: Quan điểm của tôi về việc dùng Google Workspace CLI và MCP server trong công việc hằng ngày

Sau khi đọc đặc tả và chạy thử, quan điểm chung của tôi là tích cực nhưng thận trọng. Các công cụ này rõ ràng được thiết kế bởi những người nghĩ về agent trước tiên: lệnh tự khám phá được, output JSON, các thao tác "nguy hiểm" bị lược bỏ, xác nhận ở phía server. Đồng thời đây là phiên bản đầu tiên của một hợp đồng mới giữa Google và AI agent, và một công ty nhỏ nên áp dụng nó giống như cấp bất kỳ quyền truy cập dữ liệu production nào: từ từ, quyền hẹp, và có một người chịu trách nhiệm.

4.2 Tôi chọn giữa CLI và MCP server như thế nào

  • CLI khi agent sống trong terminal. Với Claude Code hay Codex làm việc trong một repository, CLI là lựa chọn mặc định của tôi. Nó chuyển file thật giữa ổ đĩa và Drive, JSON có thể lọc bằng jq trước khi model nhìn thấy, và cùng các lệnh đó sau này có thể đưa vào script hay job định kỳ. Chi phí token thấp hơn và ít văn bản không tin cậy trong context hơn là lợi thế thật, không chỉ là tiện lợi.
  • MCP khi không có shell hoặc người dùng không phải developer. Với đồng nghiệp dùng Claude trên trình duyệt hay một chat client khác, MCP connector là lựa chọn thực tế duy nhất, và Universal Search chỉ có ở phía MCP. Việc cập nhật diễn ra phía Google, nên không phải giữ binary mới nhất trên từng laptop.
  • Dù chọn cái nào cũng chỉ một mô hình bảo mật. Vì hai đường đi dùng chung backend, chung loại client gắn cờ agent và chung cơ chế xác nhận phía server, tôi không thấy lý do phải chuẩn hoá về một cái. Một team có thể cho developer dùng CLI và người không phải developer dùng MCP, dưới cùng một bộ quy tắc.

4.3 Những giới hạn tôi thấy

  • Độ ổn định. Một sản phẩm GA nhưng nói rõ không đảm bảo tương thích ngược cho lệnh và schema output nghĩa là mọi script tôi viết đều phải coi là dễ vỡ. Agent đối phó bằng cách đọc help mỗi lần; cron job và script CI thì không.
  • Nhãn preview và lỗ hổng tài liệu. Các trang MCP vẫn ghi Developer Preview, Tasks không có endpoint MCP được mô tả, và release notes không có số version. Với dự án khách hàng cần điều khoản GA, tôi sẽ đợi tài liệu cập nhật.
  • Đăng nhập tương tác. Login cần trình duyệt trên cùng máy. Dùng headless chỉ có thể qua --oauth_token, tức là đẩy việc tạo và bảo vệ token về phía chúng ta.
  • Chênh lệch tính năng giữa CLI và MCP. Một số action chỉ có ở một phía (Tasks, trash/spam Gmail trên CLI; Universal Search, Classroom và thêm tool Chat trên MCP), nên một workflow có thể không chuyển trơn tru từ bên này sang bên kia.
  • Chi phí và mốc thời gian sắp tới. Lượng dùng được tính vào quota của project, billing bắt đầu 01/04/2027 nhưng chưa có bảng giá, và từ 01/02/2027 agent dự kiến chỉ được dùng các giao diện này. Mọi bot nội bộ gọi REST API cổ điển thay cho agent cần có kế hoạch chuyển đổi ngay từ bây giờ.
  • Chi phí token của MCP. Kết quả lớn rơi thẳng vào context của model. Với "đọc tài liệu 40 trang này" thì ổn; với "kiểm tra 500 file" thì CLI lọc bằng jq rẻ hơn rõ rệt.

Những gì bài test thực tế dạy tôi

  • "Generally available" không có nghĩa là "mở cho mọi project" ngay từ ngày đầu. Binary CLI, loại OAuth client, bước đăng nhập và MCP discovery đều hoạt động trên một project hoàn toàn mới, nhưng việc thực thi tool trên Calendar, Tasks và Gmail vẫn đòi hỏi ghi danh Developer Preview, còn Drive thì từ chối bằng một lỗi quyền chung chung. Các trang MCP vẫn mang banner Developer Preview, và trên thực tế đó mới là mô tả chính xác hơn.
  • Chất lượng thông báo lỗi khác nhau giữa các service. Calendar, Tasks và Gmail trả về thông báo chính xác, có thể hành động ngay; Drive chỉ trả về "The caller does not have permission", khiến agent (và cả con người) dễ nhầm là thiếu scope.
  • Scope rộng hơn action. Cấp create_draft sinh ra token cũng có thể gửi mail, và cấp service calendar sinh ra quyền đọc-ghi-xoá toàn bộ lịch. Hãy ghi rõ từng action cụ thể khi đăng nhập.
  • Discovery thì mở, thực thi thì bị chặn. Agent có thể liệt kê và lên kế hoạch với mọi tool trước khi biết mình không được gọi chúng. Prompt và skill nên dặn agent dừng lại và báo cáo khi gặp isError, điều mà Claude Code đã làm khi được yêu cầu báo cáo chính xác chuyện gì đã xảy ra.
  • Round trip nhanh. Các lần gọi MCP từ Việt Nam mất khoảng 0,45–1 giây; lệnh CLI tính cả thời gian khởi động process mất 1,2–4,1 giây. Tốc độ không phải lý do để chọn cách này thay vì cách kia.

4.4 Các lưu ý bảo mật

Câu "a valid token is no longer enough" của Cloud blog là mô hình tư duy đúng. Trước khi để các công cụ này chạm vào dữ liệu thật của công ty, tôi sẽ đặt ra các quy tắc dưới đây. Phần lớn không tốn chi phí.

Một nhận xét thẳng thắn về thiết kế human-in-the-loop. Đây là thiết kế tốt, và nó được cưỡng chế ở server, tốt hơn nhiều so với kiểm tra phía client. Nhưng trong CLI, quyết định đi ngược lại qua standard input, và chính tài liệu phải yêu cầu agent xin xác nhận của người dùng trước khi trả lời. Một harness tử tế như Claude Code sẽ hiện câu hỏi và hỏi tôi; một script tự viết cẩu thả pipe "ALLOW_ONCE" vào mọi lệnh sẽ âm thầm gỡ bỏ lớp bảo vệ. Vì vậy tôi coi HITL là trách nhiệm chung: Google cung cấp chốt kiểm soát, còn team phải đảm bảo không ai tự động hoá bỏ qua nó.

4.5 Khuyến nghị của tôi cho một công ty nhỏ

  1. Bắt đầu ngay với các use case chỉ đọc (chuẩn bị họp, báo cáo dọn dẹp Drive) trên client personal mode, để mọi người làm quen công cụ mà không có rủi ro.
  2. Viết một chính sách agent dài một trang: dữ liệu được phép, scope được phép, ai được duyệt scope ghi, thiết lập telemetry, và cách thu hồi.
  3. Chuyển sang cài đặt thủ công với mỗi use case một client gắn cờ agent, và để Workspace admin quản lý danh sách.
  4. Kiểm kê các script hay bot nội bộ gọi Workspace REST API thay cho AI và chuyển chúng sang CLI hoặc MCP trước 01/02/2027.
  5. Ước tính lượng sử dụng trước 01/04/2027, khi bắt đầu tính phí theo quota.

5. FAQ

gwscli có phải chỉ là một lớp vỏ bọc REST API cổ điển?

Không hẳn. Khi cài đặt một dịch vụ cho CLI, bạn bật cả API cổ điển lẫn phần MCP đi kèm (ví dụ drive.googleapis.com và drivemcp.googleapis.com), và tên action của CLI gần như trùng khớp một-một với tên tool MCP. Trên thực tế CLI hoạt động như một MCP client chạy local đóng gói thành binary, với cùng cơ chế xác thực gắn cờ agent và cùng các bước xác nhận phía server. Script gọi thẳng REST API bằng OAuth client thường là một con đường khác, và theo Workspace AI Tools Addendum, lưu lượng của agent dự kiến phải chuyển sang CLI hoặc MCP server.

Có cần tài khoản Google Workspace trả phí không?

Phần lớn dịch vụ chạy được với Google Account cá nhân ở personal mode. Chat send_message cần tài khoản Workspace và một Chat app đã cấu hình, còn lệnh People cần đăng ký Developer Preview. Trong domain công ty, chính sách của admin quyết định app và scope nào được phép.

Có miễn phí không?

Hiện chưa tính phí riêng cho CLI hay MCP server, nhưng request được tính vào quota sử dụng Workspace của Cloud project, và việc tính phí cho lưu lượng agent được công bố sẽ bắt đầu từ 01/04/2027.

Agent có tự gửi email hay chia sẻ file được không?

CLI và Gmail MCP server chỉ tạo bản nháp; con người gửi. Không có lệnh đổi quyền chia sẻ Drive. Các thao tác nhạy cảm có tồn tại (gửi tin nhắn Chat, đưa vào thùng rác) sẽ kích hoạt xác nhận phía server mà con người phải trả lời.

Có dùng chung một OAuth client cho CLI và MCP được không?

Trong bài test của tôi cả hai dùng chung một project. Hướng dẫn khuyên dùng Desktop client cho CLI và thường là Web application client cho MCP client cần đăng ký callback URL. Trong mọi trường hợp client phải được gắn cờ agent, và nên tách client của agent khỏi client của ứng dụng thường.

Có chạy được trong CI hay trên server không?

Có, với global flag --oauth_token và token từ client gắn cờ agent hoặc service account domain-wide delegation. Khi đó bạn tự chịu trách nhiệm tạo, xoay vòng và bảo vệ token, và xác nhận cho thao tác nhạy cảm vẫn áp dụng.

6. Kết luận

  • Những gì được phát hành: gwscli GA ngày 24/11/2026 dưới dạng một binary cho Linux, macOS và Windows, với output JSON, khám phá lúc chạy và agent skills nhúng sẵn; các MCP server do Google host phủ Gmail, Drive, Docs, Sheets, Slides, Calendar, Chat, People, Classroom và Universal Search; và một mô hình bảo mật xây quanh client gắn cờ agent, kiểm tra chính sách trên từng request, xác nhận của con người và quyền kiểm soát của admin, với cưỡng chế từ 01/02/2027 và tính phí từ 01/04/2027.
  • Những gì tài liệu chưa thống nhất: nhãn GA và Developer Preview, endpoint MCP cho Tasks, số version trong release notes, và một số tool chỉ có ở một phía.
  • Những gì tôi đã làm: cài gwscli 1.0.6 trên Windows, tạo project personal mode với client gắn cờ agent, đăng nhập với scope chỉ đọc, chạy kịch bản báo cáo tuần trên Drive, Calendar, Tasks và Gmail, và để Claude Code làm việc tương tự qua skills và qua MCP server remote.
  • Quan điểm của tôi: CLI cho agent trong terminal, MCP cho chat client và người không phải developer, một mô hình bảo mật cho cả hai. Lợi ích lớn nhất cho một team dev nhỏ nằm ở phần đọc và chuẩn bị trong công việc hằng ngày; bước cuối không thể hoàn tác nên để con người làm, và đó cũng chính là cách Google thiết kế.

Mọi file, sự kiện, task và bản nháp trong bài đều do tác giả tạo để thử nghiệm. Không sử dụng dữ liệu khách hàng hay dữ liệu bảo mật của công ty. Client ID, secret, token và địa chỉ email đều đã được che. Thông số được đối chiếu với các trang chính thức ngày 25/11/2026 và có thể thay đổi.
