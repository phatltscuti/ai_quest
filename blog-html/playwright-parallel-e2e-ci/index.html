1. Method overview

The Zenn article from Berry describes how their team runs about 100 Playwright specs / 140 test cases for a QMS SaaS product on every pull request in roughly 6–8 minutes of wall-clock time. That duration is close to their unit-test and lint jobs, which means E2E can stay inside the normal PR feedback loop instead of being deferred to a nightly batch.

The core idea is that Playwright worker settings alone are not enough. Parallel E2E only becomes reliable after the suite is redesigned around four layers:

  1. Test structure for isolation: each test creates its own data through fixtures/factories, tears it down afterward, and avoids shared mutable state. Login cost is reduced with storageState. Specs stay scenario-focused while locators and waits live in Page Objects.
  2. Two-level parallelization: GitHub Actions matrix jobs split work by {load}-{release}-{feature} projects, and each job then runs Playwright workers. Light tests use higher parallelism; heavy tests that call slow Edge Functions use fewer workers and longer timeouts.
  3. Infrastructure tuning under load: higher concurrency exposed PostgREST pool exhaustion and a Kong keep-alive reuse race that produced intermittent 502s. They fixed the race structurally rather than hiding it with retries, and kept host-level instrumentation so worker counts could be chosen from measurements.
  4. Operational discipline: an “Iron Law” forbids fixed sleeps and sync DOM snapshot asserts, CI retries stay at zero, impact maps run only affected specs for app PRs, and AI agent skills encode the same quality bar for humans and generated tests.

Before the redesign, their old suite ran only on a weekday morning schedule, took 30–56 minutes, and was repaired only when someone happened to notice failures. After the redesign, E2E became a normal merge gate.

2. Implementation steps

The article does not present a single copy-paste tutorial for every repository. Objectively, the implementation path looks like this:

2.1. Redesign tests for data independence

  1. Stop sharing documents, users, or workflow state across tests.
  2. Create per-test fixtures that insert dedicated data and tear down derived records.
  3. Prepare authentication with storageState instead of logging in through the UI in every test.
  4. Provide multiple accounts per role so parallel workers do not fight over the same user.
  5. Move locators, clicks, and waits into Page Objects; keep specs as S/E scenario steps.

2.2. Split Playwright projects by load profile

  1. Tag slow or externally bound cases as heavy; keep ordinary UI/CRUD cases light.
  2. Configure light projects with fullyParallel: true and higher workers.
  3. Configure heavy projects with fewer workers, longer timeouts, and less aggressive parallel overlap.
  4. Tune worker counts per domain after measuring CPU pressure and failure modes.

2.3. Build CI as matrix × fresh full stack

  1. Split jobs by project on GitHub Actions, preferably on dedicated larger runners.
  2. Start a real local backend stack per job when the product depends on auth, RLS, storage, or edge functions.
  3. Pin tool versions, cache browsers, cancel outdated concurrent runs, and install required fonts for evidence screenshots.
  4. Raise connection pools and fix gateway keep-alive mismatches that only appear under parallel load.
  5. Keep host metrics in the job summary so “test bug” and “too many workers” can be distinguished.

2.4. Add impact-based execution and anti-flake rules

  1. Map changed paths to affected specs with first-match rules and fail-open fallback.
  2. Run full E2E when test code itself changes; run impact E2E for ordinary app changes.
  3. Ban waitForTimeout; wait for UI or network state instead.
  4. Use web-first assertions, positive landmarks before absence checks, and zero CI retries.
  5. Keep videos, screenshots, and traces as investigation evidence.
Berry’s production numbers depend on Larger Runners, Supabase, Kong tuning, and a mature suite. A practice project can validate the method’s shape, but it will not reproduce their exact 6–8 minute timing for 140 cases.

3. Hands-on practice and results

Because the original QMSmart stack is private, I implemented a local practice demo that captures the transferable parts of the method:

  • a mini document workflow app (draft → review requested → approved)
  • per-test fixtures with unique titles and teardown
  • Page Object Model with state-based waits only
  • light and heavy Playwright projects
  • an impact-map resolver with first-match and fail-open behavior
  • a sample GitHub Actions matrix workflow

The practice package lives in blog-html/playwright-parallel-e2e-ci/practice-demo/. Setup and commands are documented in HUONG-DAN-DEMO.md.

Master setup commands

cd blog-html/playwright-parallel-e2e-ci/practice-demo
npm install
npx playwright install chromium
npx playwright test
node scripts/resolve-impact.js app/index.html
npx playwright test --project=light-r1-document
npx playwright test --project=heavy-r1-document

Key config practiced

// light: higher parallelism for ordinary UI/CRUD
fullyParallel: true
workers: 3–4

// heavy: slower path that simulates Edge Function work
fullyParallel: false
workers: 2
timeout: 60_000

Execution results on this machine

  • Full suite: 3 passed in about 10.0s using 3 workers.
  • Light project only: 2 passed in about 4.6s.
  • Heavy project only: 1 passed in about 7.3s.
  • Impact resolve for app/index.html: matched document-ui and selected both specs.
  • Impact resolve for the heavy spec file: matched document-heavy-only and selected one spec.

The light tests covered draft creation, review request, task-list visibility, and audit-log evidence. The heavy test walked the same flow into an approval step with an intentional delay to represent a slow edge-style operation. No waitForTimeout calls were used in Page Objects or specs.

Detailed command logs are stored under demo-assets/, including 01-full-suite-run.txt, impact resolver outputs, and project-only runs. The summarized evidence is in demo-assets/06-demo-run-log.md.

What this practice proved: the architecture works locally and stays readable. What it did not claim: reproduction of Berry’s Kong 502 root-cause fix, PSI monitoring, or their production CI wall-clock.

4. Opinion and daily-work application

My main takeaway is that “make Playwright faster” is the wrong starting question. The useful question is whether the suite is safe to run in parallel. Once tests own their data, avoid shared accounts, and hide waits inside Page Objects, worker count becomes a tuning dial instead of a source of random failures.

For my own daily work, I would apply this in four practical ways:

  1. PR feedback for UI features: keep a small, always-on light suite for critical flows, and isolate slow integrations as heavy so they do not block ordinary reviews.
  2. Impact gating before push: maintain a simple path-to-spec map so local and CI run the same affected set. That reduces “I only changed copy, why did the whole suite run?” cost without silently skipping risk.
  3. Flake reduction as team policy: treat Iron Law rules as review criteria. Ban fixed sleeps, require web-first assertions, and keep CI retries at zero so flaky tests stay visible.
  4. Measure before raising concurrency: if parallel jobs start failing with timeouts or gateway errors, inspect infrastructure limits first. Raising workers without telemetry recreates the article’s old failure mode in a new form.

Even outside a regulated QMS product, the URS-style S/E step naming is worth borrowing. Specs become easier to read in failure reports, and the same structure helps when AI tools generate or revise tests because the quality bar is explicit.

5. Conclusion

Berry’s article shows a complete method for turning E2E from a slow overnight burden into a PR-native quality gate: isolate data, split light and heavy work, tune CI under real load, and enforce anti-flake rules mechanically.

The local practice demo confirms that the transferable core is implementable without their full production stack. With fixtures, POM, project splits, and impact selection in place, a small suite already runs cleanly in seconds and stays understandable. Scaling further is then an operations problem—runners, pools, gateway timeouts, and measurement—not only a Playwright config problem.
