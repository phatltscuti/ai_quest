Trạng thái thực hành: đã dựng mini demo local và chạy thành công trên máy này. Full suite: 3 passed trong khoảng 10 giây. Demo tập trung vào kiến trúc có thể chuyển giao từ bài viết, không tái tạo toàn bộ stack Supabase/Kong production của Berry.

1. Tổng quan phương pháp

Bài viết của Berry mô tả cách team họ chạy khoảng 100 Playwright spec / 140 test case cho sản phẩm QMS SaaS trên mỗi pull request với wall-clock khoảng 6–8 phút. Thời gian này gần với job unit test và lint, nên E2E có thể nằm trong vòng phản hồi PR thông thường thay vì bị đẩy sang nightly batch.

Ý chính là chỉ tăng workers của Playwright thì chưa đủ. E2E song song chỉ ổn định sau khi suite được thiết kế lại theo bốn lớp:

  1. Cấu trúc test độc lập dữ liệu: mỗi test tự tạo data qua fixture/factory, teardown sau khi chạy, không chia sẻ state. Giảm chi phí login bằng storageState. Spec chỉ mô tả kịch bản; locator và wait nằm trong Page Object.
  2. Song song hai tầng: GitHub Actions matrix chia job theo project {load}-{release}-{feature}, mỗi job lại chạy Playwright workers. Test light dùng song song cao hơn; test heavy gọi Edge Function chậm thì giảm workers và tăng timeout.
  3. Tối ưu hạ tầng khi tải tăng: song song hóa làm lộ giới hạn pool PostgREST và race keep-alive của Kong gây 502. Họ xử lý tận gốc thay vì giấu bằng retry, đồng thời giữ instrumentation để chọn số workers dựa trên đo đạc.
  4. Kỷ luật vận hành: “Iron Law” cấm sleep cố định và assert snapshot DOM đồng bộ, CI giữ retries = 0, impact map chỉ chạy spec bị ảnh hưởng cho PR app, và AI skill mã hóa cùng một tiêu chuẩn chất lượng cho người lẫn AI.

Trước khi redesign, suite cũ chỉ chạy vào buổi sáng ngày thường, mất 30–56 phút, và chỉ được sửa khi có người tình cờ để ý failure. Sau redesign, E2E trở thành điều kiện merge bình thường.

2. Các bước triển khai

Bài viết không phải tutorial copy-paste cho mọi repo. Nhìn khách quan, lộ trình triển khai gồm các bước sau:

2.1. Thiết kế lại test để độc lập dữ liệu

  1. Ngừng chia sẻ document, user, hoặc workflow state giữa các test.
  2. Tạo fixture theo từng test để insert data riêng và teardown bản ghi phát sinh.
  3. Chuẩn bị auth bằng storageState thay vì login UI mỗi lần.
  4. Chuẩn bị nhiều account cho mỗi role để worker song song không tranh nhau.
  5. Đưa locator, click và wait vào Page Object; giữ spec ở dạng bước S/E.

2.2. Tách Playwright project theo hồ sơ tải

  1. Gắn tag heavy cho case chậm hoặc phụ thuộc I/O ngoài; case UI/CRUD thường để light.
  2. Cấu hình light với fullyParallel: true và workers cao hơn.
  3. Cấu hình heavy với ít workers hơn, timeout dài hơn, ít chồng chéo hơn.
  4. Chỉnh số workers theo từng domain sau khi đo CPU pressure và kiểu lỗi.

2.3. Dựng CI dạng matrix × full stack sạch

  1. Chia job theo project trên GitHub Actions, ưu tiên runner riêng/dedicated nếu có.
  2. Mỗi job khởi động backend thật nếu sản phẩm phụ thuộc auth, RLS, storage, edge function.
  3. Pin version tool, cache browser, hủy run cũ khi push liên tiếp, cài font nếu cần cho ảnh chứng cứ.
  4. Tăng connection pool và sửa lệch keep-alive của gateway chỉ lộ khi chạy song song.
  5. Giữ metric host trong Job Summary để tách “bug test” khỏi “workers quá cao”.

2.4. Thêm chạy theo impact và luật chống flaky

  1. Ánh xạ đường dẫn file đổi sang spec bị ảnh hưởng bằng first-match và fail-open.
  2. Đổi test code thì chạy full E2E; đổi app thì chạy impact E2E.
  3. Cấm waitForTimeout; chỉ wait theo trạng thái UI hoặc network.
  4. Dùng web-first assertion, landmark dương trước khi check vắng mặt, retries CI = 0.
  5. Giữ video, screenshot và trace làm bằng chứng điều tra.
Số liệu production của Berry phụ thuộc Larger Runner, Supabase, chỉnh Kong và suite trưởng thành. Project thực hành có thể kiểm chứng hình dạng phương pháp, nhưng không tái tạo đúng mốc 6–8 phút cho 140 case.

3. Thực hành và kết quả

Vì stack QMSmart gốc là private, tôi dựng một demo local nắm các phần có thể chuyển giao:

  • mini app quy trình document (draft → review requested → approved)
  • fixture theo test với title duy nhất và teardown
  • Page Object Model chỉ dùng state-based wait
  • Playwright project light và heavy
  • impact-map resolver theo first-match và fail-open
  • mẫu workflow GitHub Actions matrix

Package thực hành nằm ở blog-html/playwright-parallel-e2e-ci/practice-demo/. Cách chạy nằm trong HUONG-DAN-DEMO.md.

Lệnh setup chính

cd blog-html/playwright-parallel-e2e-ci/practice-demo
npm install
npx playwright install chromium
npx playwright test
node scripts/resolve-impact.js app/index.html
npx playwright test --project=light-r1-document
npx playwright test --project=heavy-r1-document

Config đã thực hành

// light: song song cao hơn cho UI/CRUD thường
fullyParallel: true
workers: 3–4

// heavy: nhánh chậm mô phỏng Edge Function
fullyParallel: false
workers: 2
timeout: 60_000

Kết quả chạy trên máy này

  • Full suite: 3 passed trong khoảng 10.0s với 3 workers.
  • Chỉ light: 2 passed trong khoảng 4.6s.
  • Chỉ heavy: 1 passed trong khoảng 7.3s.
  • Impact resolve app/index.html: khớp rule document-ui, chọn cả hai spec.
  • Impact resolve file heavy: khớp document-heavy-only, chọn một spec.

Test light phủ tạo draft, request review, hiện task list và audit log. Test heavy đi tiếp sang bước approve với delay chủ đích để mô phỏng thao tác edge chậm. Page Object và spec không dùng waitForTimeout.

Log lệnh chi tiết nằm trong demo-assets/, gồm 01-full-suite-run.txt, output impact resolver và các lần chạy theo project. Bản tóm tắt nằm ở demo-assets/06-demo-run-log.md.

Demo này chứng minh kiến trúc chạy được và dễ đọc ở local. Demo không tuyên bố đã tái tạo fix Kong 502, PSI monitoring, hay wall-clock CI production của Berry.

4. Ý kiến và ứng dụng công việc hằng ngày

Bài học lớn nhất với tôi là câu hỏi đúng không phải “làm sao để Playwright nhanh hơn”, mà là “suite đã an toàn để chạy song song chưa”. Khi mỗi test tự sở hữu data, không tranh account, và nhốt wait trong Page Object, số workers trở thành núm chỉnh thay vì nguồn flake.

Trong công việc hằng ngày, tôi sẽ áp dụng theo bốn hướng thực tế:

  1. Phản hồi PR cho tính năng UI: giữ một light suite nhỏ luôn chạy cho flow quan trọng, tách tích hợp chậm thành heavy để không chặn review thông thường.
  2. Impact gate trước khi push: duy trì map path → spec đơn giản để local và CI chạy cùng một tập bị ảnh hưởng. Giảm chi phí “chỉ sửa copy mà chạy cả suite”, nhưng không bỏ sót rủi ro một cách im lặng.
  3. Giảm flake bằng quy ước nhóm: đưa Iron Law vào tiêu chí review. Cấm sleep cố định, bắt buộc web-first assertion, giữ retries CI = 0 để flake vẫn lộ ra.
  4. Đo trước khi tăng concurrency: nếu job song song bắt đầu timeout hoặc lỗi gateway, hãy xem giới hạn hạ tầng trước. Tăng workers khi chưa có telemetry chỉ tạo lại kiểu thất bại cũ dưới hình thức mới.

Ngay cả ngoài sản phẩm QMS chịu kiểm soát, cách đặt tên bước S/E theo URS vẫn đáng học. Spec dễ đọc hơn trong báo cáo lỗi, và cùng cấu trúc đó giúp AI tạo/sửa test vì tiêu chuẩn chất lượng đã được viết rõ.

5. Kết luận

Bài của Berry cho thấy một phương pháp trọn vẹn để biến E2E từ gánh nặng overnight thành cổng chất lượng gắn với PR: cô lập data, tách light/heavy, tối ưu CI dưới tải thật, và ép luật chống flake một cách máy móc.

Demo thực hành local xác nhận phần lõi có thể chuyển giao mà không cần full stack production. Với fixture, POM, project split và impact selection, một suite nhỏ đã chạy sạch trong vài giây và vẫn dễ hiểu. Muốn scale tiếp lúc đó là bài toán vận hành—runner, pool, gateway timeout và đo đạc—không chỉ còn là chỉnh config Playwright.
