Self-Evolving Search Index – When an index learns how to be found

Summary of arXiv:2609.19656 – Self-Evolving Search Index (Sangam Lee, Wonjae Lee, Sunghwan Kim, Deogyong Kim, Jaehoon Kim, Daye Nam, SeongKu Kang, Dongha Lee; Yonsei University, Samsung Research, UC Irvine, Korea University). Submitted 17 Sep 2026, cs.IR / cs.AI, marked “Work in progress”.

Almost every RAG or AI-agent project we build shares a quiet bottleneck: the document does contain the answer, but the retriever does not find it, because the way the document is indexed does not match the way users ask. This paper proposes Self-Index: an LLM diagnoses where the index is weak, rewrites the “index keys”, validates them, and repeats – with no relevance labels, no retriever retraining, and no change to the documents themselves.

  • Headline result: on BRIGHT, average nDCG@10 rises by +38.8% to +57.0% depending on the retriever, while the best prior method gains about 9–13%.
  • Downstream: search agents answer more accurately and call search less often; agent memory systems recall past experience better (+9.2% to +13.9%).
  • Takeaway for Scuti: a “measure → diagnose → selectively fix → validate” loop that we can apply right away to RAG projects over Japanese clients’ documents.

1. Background: what is an index key and why does it matter?

A retriever (BM25 or an embedding model) does not compare a question with the “meaning” of a document; it compares it with whatever was put into the index to represent that document. The paper calls these representations index keys. By default the only key is the raw text (or chunk). Each document d has a key set K(d), and the document’s score for query q is the score of its best-matching key: 

score(q, d) = max over k in K(d) of rel(q, k)      // rel = cosine similarity or BM25

Enriching an index is not new: Doc2Query generates pseudo-questions per document, Anthropic’s Contextual Retrieval adds context/summaries, EnrichIndex adds purpose + summary + QA pairs, SPIKE adds user “scenarios”… The paper points out two problems:

  • No fixed strategy wins everywhere. Corpus type (prose, code, math, tables) and retriever type (sparse/dense) favour different key forms. In the paper, Doc2Query strongly helps BM25 on tables but hurts code, and lowers the average for dense retrievers.
  • Refinement is still done by humans: someone has to inspect failing queries, guess which keys are at fault, edit the prompt/strategy (or label more data and retrain), and reprocess the whole corpus – slow, expensive, and repeated whenever new failures appear.
The paper’s question: can an index evolve by itself to fit its retrieval environment – finding its own failures, fixing only what needs fixing, validating its own changes – without humans and without relevance labels?

2. Main contributions

  1. The Self-Index framework – brings the “self-evolving” paradigm (already used for LLMs/agents that improve themselves) to index optimization. The index diagnoses and refines its own keys across diverse retrieval demands.
  2. Consistent gains across environments: 3 retrievers (BM25, BGE-Large, Qwen3-Embedding-8B) × 4 corpus types (natural language, code, math, tables). Self-Index has the best average for every corpus type under every retriever, beating Doc2Query, SPIKE, RL-Index and EnrichIndex.
  3. Downstream benefits: search agents (BrowseComp-Plus) become more accurate with fewer search calls and lower online cost; agent memory (LongMemEval-V2) retrieves useful past interactions better.

The official code is at github.com/augustinLib/Self-Index.

3. Method: the Optimizer (3 stages) + the Query Simulator

3.1. Ground rules

  • Never touch the document, only its “entrances”: the original text is always kept as a fixed key, never revised or validated. Generated keys can be added, dropped or rewritten.
  • Max-score instead of weighted fusion: earlier methods (SPIKE, EnrichIndex) need tuned weights to combine representations. Self-Index takes the max, removing one more knob a human would have to tune.
  • Budget: at most 10 keys per document, including the original-text key.

3.2. The Optimizer – a three-stage loop

The Optimizer is an LLM (Qwen3.6-35B-A3B in the main experiments) that can call the retriever and edit keys. Each iteration takes a batch of 128 queries and retrieves the top-30 keys per query.

StageWhat it doesSubtle point
① Self-Diagnosis Runs the queries over the current index. For each retrieved key it builds a co-retrieval profile: which keys of other documents tend to appear alongside it, and how often. The LLM reads the document + its keys + these profiles and returns JSON: which key falls short, why, and how the key set should change (without writing new keys yet). No relevance labels needed – inspired by pseudo-relevance feedback (Rocchio). Co-retrieval reveals which documents a key fails to distinguish from.
② Self-Revision Only diagnosed documents are revised. The whole key set of a document is revised once per iteration (avoiding redundant keys). The LLM sees the “competing keys” of rival documents so it knows which distinctions to stress. No predefined strategy: the LLM decides key form and length itself. The prompt asks for keys “in the words a searcher would use, not in the document’s words”.
③ Self-Validation Every generated key (including kept ones) must pass three checks. Failing keys are dropped; if no newly proposed key survives, the old key set is kept. Two of the three checks reuse the retriever’s own relevance function – no extra LLM calls.

The three validation criteria (grounded in Salton’s classic principles of good index terms):

  • Faithfulness: an LLM judge scores 0–3 whether the document really resolves the need the key describes; ≥ 2 is required. Blocks hallucinated keys.
  • Specificity: the key is used as a query over the whole corpus; its source document must appear in the top-K. Keys that are too generic get dropped.
  • Separation: the key’s maximum similarity to the competing keys must be lower than that of the current key set – the new key has to make the document stand out, not blend in.

3.3. Query Simulator – from reactive to proactive

With the Optimizer alone, the index can only fix failures exposed by the queries it sees (reactive). The Query Simulator actively looks for demands nobody has asked yet (Self-Exploration):

  1. Sample n documents at random.
  2. First LLM call: describe the problem or confusion a person who has not read the document would have, without the document’s jargon or names.
  3. Second call: role-play that person and write m forum-style questions – without seeing the original document, to avoid copying its wording.
  4. Filter by Answerability (LLM judge ≥ 2/3) and Dissimilarity (word-set Jaccard < 0.8 against every query already used).
Worth noting: in the main experiments all optimization queries come from the Query Simulator (20 iterations × 128 = 2,560 queries). Evaluation queries are never seen during optimization, so the gains are not from “studying the test”.

4. Experimental results

The paper answers three research questions: (RQ1) does it work across corpora and retrievers, (RQ2) does it help search agents, (RQ3) does it help agent memory. The retrieval metric is nDCG@10.

On three table retrieval datasets (Spider 2.0, FIBEN, BEAVER – finding the right table in a DB schema) the average gain is +49.1% (BM25), +17.9% (BGE) and +16.2% (Qwen3-Emb), above EnrichIndex (+42.4%, +13.3%, +11.2%). Doc2Query actually hurts dense table retrieval (−3.2%, −7.1%) – evidence for “no fixed strategy wins everywhere”.

  • Self-Index gives the highest accuracy and evidence recall in all 8 settings and reduces search calls in all 8 (SPIKE sometimes increases them).
  • Gains are largest with a weak retriever (BM25); with a strong one (Qwen3-Emb-8B) accuracy gains are smaller (+3% to +23%).
  • Fewer search calls → fewer tokens → lower online cost. GPT-5.4-nano + BM25 with Self-Index matches the accuracy of DCI (an index-free agent that reads the corpus directly) with the same backbone, at lower cost.
  • When the corpus grows from 100K to 400K documents, Self-Index keeps accuracy stable without raising per-query cost, while SPIKE and especially DCI lose accuracy and get more expensive (Figure 3).

4.3. RQ3 – Agent memory (LongMemEval-V2)

Self-Index only changes retrieval keys; memory contents stay the same. Overall accuracy:

Gains appear in static, dynamic and workflow abilities, but not in “gotchas” (it even drops from 0.276 to 0.241 for Query → Slice), because gotchas depend more on how memory is built than how it is retrieved. A very practical case: the agent needs the ServiceNow offboarding procedure for employee A, but memory only holds an offboarding run for employee B. The evolved key “automated employee offboarding hardware unassignment workflow” finds the old experience despite the different name, and the agent picks the right procedure.

  • Query source: replacing the Query Simulator with existing synthetic queries (ReasonIR HQ) still beats the base index (NL 18.1 → 24.3), but the Query Simulator is better for every corpus type (NL 26.6, Code 22.1, Math 17.2). So the Optimizer also works with real user query logs.
  • Progressive evolution: Self-Index passes SPIKE within a few iterations and keeps improving up to iteration 20 (Figure 6).
  • LLM backbone: a 0.8B model is too weak (drops below base on 3 of 5 datasets); 9B and above all help; Qwen3.6-35B-A3B is best (22.4), a 304B model is not better (19.9). Bigger is not automatically better.

6. Limitations and things to read carefully

  • This is v1, self-described as “Work in progress”, not yet peer-reviewed.
  • Not every cell is a win: on LeetCode Self-Index is below the base index with BM25 (22.4 vs 24.4) and BGE (24.7 vs 26.8); on Spider 2.0 + BM25, EnrichIndex is higher (44.0 vs 42.3). The claim is about per-corpus-type averages, not every dataset.
  • Gains shrink when the retriever is already strong (Qwen3-Emb-8B on BrowseComp-Plus: +3% to +23% accuracy).
  • Offline cost counts token prices only, not GPU/hosting; the math dataset saves little (12.5%).
  • Corpora in the experiments are static; frequently changing documents are not evaluated.

7. Personal learnings & how to apply them at Scuti AI

At Scuti most AI projects for Japanese clients are chatbots/RAG over internal documents (仕様書 specifications, マニュアル manuals, FAQs, tickets, DB schemas) and, increasingly, business-automation agents. Reading this paper changed how I want to work in a few ways:

7.1. What I learned

  1. RAG failures often sit at the “entrance”, not in the LLM. When a chatbot answers wrongly, our reflex is to tweak the prompt or swap the model. Here, changing only the index keys (same retriever, same documents) raised agent accuracy by up to +78–90%. Next time I will check retrieval first.
  2. “Write keys in the searcher’s words” – especially true for Japanese clients: end users ask in everyday Japanese (「パスワードを忘れた時どうする？」) while documents use technical terms or English. That vocabulary gap is exactly what Self-Index narrows.
  3. LLM-generated content without validation is worse than doing nothing. Removing Self-Validation fell below the base index. The same applies to every LLM pipeline we run: summaries, generated test cases, spec translation… all need an explicit validation gate.
  4. Selective fixes are cheaper than full rebuilds. Touching only problematic documents saved 72–73% versus regenerating keys for the whole corpus – like fixing by bug report instead of refactoring everything.
  5. Co-retrieval is a free debugging signal. Documents that always come back together are often duplicates, old/new versions, or have keys that are too generic – very useful when cleaning a client’s knowledge base.
  6. Keep the test set separate from optimization data. The paper never uses evaluation queries during optimization. Japanese clients value objective numbers, so we should keep a fixed test set to report before/after.

7.2. Applying it to current projects

7.3. Applying it to daily operations

  • Internal knowledge base (project wiki, Backlog, QA procedures): each month take the “no result” searches as input, let an LLM propose extra keys/tags, and have a human approve before merging – a human-in-the-loop version of Self-Validation.
  • Reviewing LLM output with three questions from the paper: is it faithful to the source? is it specific to this case? is it distinguishable from similar items?
  • Client data security: the loop needs an LLM to read every document, so NDA-heavy projects must use a self-hosted model (the paper’s open Qwen3.6-35B-A3B is a viable option) or a client-approved endpoint.

8.3. A “mini” version for your own RAG project

My own simplified pseudo-code (condensed from Algorithms 1–3); works with any vector DB that lets several vectors point to one doc_id:

for it in range(N_ITER):
    queries = simulate_queries(sample(corpus, n))          # or real search logs
    results = {q: retrieve_keys(q, top_k=30) for q in queries}
    profiles = build_co_retrieval_profiles(results)        # which keys co-occur with which
    for doc in docs_hit_by(results):
        diag = llm_diagnose(doc, keys[doc], profiles)      # JSON: weak keys + revision guidance
        if not diag.shortfalls: continue
        proposal = llm_revise(doc, keys[doc], diag, competing_keys(doc))   # max 10 keys
        passing = [k for k in proposal
                   if faithful(doc, k) >= 2                  # LLM judge 0-3
                   and doc in search_docs(k, top_k=30)      # Specificity
                   and max_sim(k, competing) < max_sim(keys[doc], competing)]  # Separation
        if any(k not in keys[doc] for k in passing):
            keys[doc] = [doc.text] + passing                 # original text always kept
evaluate(test_queries)   # separate test set, never used above
Starter tip: you do not need the full loop on day one. “Original chunk + a few question-style keys + a Specificity filter (the key must retrieve its own document)” is already a cheap, measurable improvement that is easy to explain to a client.

10. Conclusion

Self-Index turns index optimization from repetitive manual work into a controlled automatic loop: diagnose from retrieval signals → fix only where needed → validate strictly → proactively explore new demands. The most striking result is not just higher nDCG but search agents that are both more accurate and cheaper.

Three things to do now:

  1. Add a retrieval measurement step (Recall@k / nDCG@10 on a fixed test set) to every RAG project before touching prompts.
  2. Try “original chunk + question-style keys + max-score + Specificity filter” on one live Japanese RAG project.
  3. Put Faithful / Specific / Separated into the review checklist for LLM-generated content.
