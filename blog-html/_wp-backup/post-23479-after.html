A hands-on benchmark of gemini-decision-1 against Gemini 3.5 Flash-Lite on invoices, quotations, contracts, CVs and more, in Vietnamese, English and Japanese, with every request timed and priced.

1. Why classification needs a different API

This post benchmarks the Gemini Decisions API against traditional text generation for document classification. Most "AI classification" code I have written or reviewed looks the same. We send a document to a chat model, ask it to "return JSON with a category", parse the text, and hope the model did not add an extra field, change a label's spelling, or think for eight seconds before answering. The model writes text so that our code can turn the text back into a decision.

Google's new Gemini Decisions API (model gemini-decision-1, announced 11 November 2026) removes that round-trip. You send an input and a set of typed questions. The model scores the candidate answers in a single pass and returns probabilities, with zero output tokens. I wanted to know whether this is a real improvement or just a new wrapper, so I built a small but realistic benchmark and ran it end-to-end.

What this post tests: the same 40 documents, the same 8 labels and the same wording of the question, sent to (A) the Decisions API, (B) the Decisions API with resolution: "low", and (C) the "traditional" approach, Gemini 3.5 Flash-Lite with a JSON response schema. Each method ran 3 times. All data is synthetic and fictional, and no customer or internal documents were used.

Where each requirement is answered

2. What the Gemini Decisions API actually returns

There is no prompt template and no "answer in JSON". A request has two parts: a shared input (text, images, PDFs, audio or video, up to about 256K tokens) and a map of questions. Each question has one of three types:

Pricing is the second half of the story. It costs $0.10 per 1M input tokens and $0 for output, and the shared input is billed once no matter how many questions you ask. For comparison, Gemini 3.5 Flash-Lite costs $0.30 per 1M input tokens and $2.50 per 1M output tokens (including thinking). Prices come from the AI Studio pricing page, checked 20 November 2026.

Practical note: the API itself worked on my free-tier key. The "Decisions API Playground" app in AI Studio, however, asked me to link a key with billing enabled, so I tested only through the Python SDK (google-genai 3.6.1, api_version="v1beta").

Scoring instead of generating: why the shape of the answer matters

It helps to be precise about what changes compared with a chat model, because every later result follows from it. This is my reading of the announcement and the API surface, not a description of Google's internals.

A generative model answers a classification question by writing. Even with a JSON schema it produces the answer token by token: an opening brace, a key, a quote, the label, a closing brace, and any other fields you asked for. Each token is a separate decoding step, so latency grows with the length of the answer, and you pay the (much higher) output price for every one of those tokens. The label you finally parse is the one string the model happened to write. If you ask it how confident it is, you get another written number, which is a guess about itself rather than a measurement.

The Decisions API turns the question around. You hand it the candidate answers up front (the keys of a choice, the yes/no of a noul, the levels of a score) and it returns how likely each one is given the input. Nothing is written, so there are no output tokens to pay for or to wait for, and the label is always one of your keys, never a misspelling or an invented class. The probabilities come from the model's own scoring, which is why they move when the input is ambiguous. That is the property I care most about, and section 7 tests it directly.

  • Consequence for speed: no decoding loop, so response time should depend mainly on reading the input. My latency numbers are consistent with that: the slowest Decisions requests were the large photo files, not the documents with the most tokens.
  • Consequence for cost: the bill is input tokens × $0.10 per million and nothing else. Asking more questions about the same input mostly adds the question text, not another copy of the document.
  • Consequence for code: no JSON parsing, no retry-on-malformed-output, no label normalisation. The response is already typed.
  • The trade-off: the API can only choose between answers you anticipated. It cannot extract a value, summarise, or tell you that your label set is missing a category, unless you add an "other" option yourself.

3. Test design: dataset, methods, metrics

Dataset

A script generates 40 fictional business documents: 8 types × 5 samples, in Vietnamese, English and Japanese. Each comes with a ground-truth label and a "has signature" flag. To keep it from being too easy, 24 of the 40 are deliberately hard:

Labels: invoice, quotation, receipt, contract, leave_request, resume, meeting_minutes, delivery_note. 8 files are PDFs and 32 are PNGs.

Methods

  • A. Decisions API: one request per document with two questions, doc_type (choice, 8 options with one-line descriptions) and has_signature (noul).
  • B. Decisions API, low resolution: same as A, with "resolution": "low" on the image block.
  • C. Text generation (baseline): gemini-3.5-flash-lite with the same descriptions in the prompt, response_mime_type="application/json", an enum schema and temperature=0. I also asked it for a self-reported confidence.

I also tried gemini-3.8-flash and gemini-3.6-flash as a stronger text-generation baseline. On image inputs, single calls did not return within 60 seconds in my environment, so I excluded them rather than report partial numbers.

Metrics

  • Accuracy of doc_type against ground truth (mean of 3 runs), plus signature accuracy.
  • Stability: share of documents that got the same label in all 3 runs.
  • Latency: wall-clock time per request from my laptop in Vietnam (p50/p95), sequential calls. Retries after rate limits are not counted.
  • Cost: computed from the actual token usage returned by each API, at list price.

4. Step-by-step implementation

Step 1: Environment

python -m venv .venv; .\.venv\Scripts\Activate.ps1
pip install google-genai pillow matplotlib python-dotenv
# .env (never committed, never printed):  GEMINI_API_KEY=...

Step 2: Generate the dataset

A short Pillow script renders each document from fictional templates (company, people, line items, totals), optionally draws a scribble on the signature line, then applies the "hard" transformations (remove title, rotate + blur + noise, downscale). It writes the ground truth to a CSV: file, doc_type, has_signature, lang, difficulty. Any similar set of your own non-confidential samples works the same way.

Step 3: The Decisions API call

The whole classifier is one call. Note that instructions is required for choice questions; the SDK rejects the request before sending if it is missing.

client = genai.Client(api_key=key, http_options={"api_version": "v1beta"})
r = client.decisions.create(
    model="gemini-decision-1",
    input=[{"type": "image", "data": b64, "mime_type": "image/png"}],   # "document" for PDFs
    questions={
        "doc_type": {"type": "choice", "instructions": Q_TYPE, "criteria": CLASSES},
        "has_signature": {"type": "noul", "instructions": Q_SIGN},
    })
label = r.answers["doc_type"].choice          # e.g. "quotation"
conf  = r.answers["doc_type"].confidence      # e.g. 0.97
probs = r.answers["doc_type"].probabilities   # all 8 options
tokens = r.usage.total_input_tokens           # output is always 0

Step 4: The traditional baseline

r = client.models.generate_content(
    model="gemini-3.5-flash-lite",
    contents=[types.Part.from_bytes(data=img, mime_type="image/png"), PROMPT],
    config=types.GenerateContentConfig(
        response_mime_type="application/json", response_schema=SCHEMA, temperature=0))
j = json.loads(r.text)    # {"doc_type": "...", "has_signature": true, "confidence": 0.99}

Step 5: One request, three question types

One request asks a choice, a yes/no and a score question about one quotation. It cost 1,354 input tokens and took about 1 second.

Step 6: Run the benchmark and build the report

The benchmark loops over the 40 documents for each method, sends one request per document sequentially, measures wall-clock time around the call, reads token usage from the response (usage.total_input_tokens for Decisions; usage_metadata.prompt_token_count, candidates_token_count and thoughts_token_count for Flash-Lite), and multiplies by list prices. On a 429 it waits and retries, and the waiting time is not counted as latency. Each method ran 3 times, then the results were aggregated into the tables and charts below.

6. Comparison results: accuracy, processing speed and API cost

40 documents × 3 runs × 3 methods = 360 requests.

What the numbers say

  • Accuracy is a tie on document type. On this dataset both approaches classified the 8 types correctly, even without titles, on rotated blurry photos and in Japanese. The task is not hard enough to separate them on accuracy alone, and that is a finding too: for a typical back-office set of document types, you do not need a generative model to get the label right.
  • Speed is where the gap is. Decisions returns in about 754 ms at the median, against 3.34 s for Flash-Lite, roughly 4× faster. Flash-Lite spends the extra time producing about 32 output tokens of JSON, and the latency varies more (p95 9.47 s).
  • Cost: 3.4× cheaper at the default resolution and 6.9× cheaper with resolution: "low", which halved the image tokens without hurting type accuracy here. Input token counts are similar for both APIs; the saving comes from the lower input price and from paying nothing for output.
  • Confidence is useful, not decorative. Flash-Lite's self-reported confidence was 0.99–1.00 on almost every document, so it tells you nothing about which answers to double-check. The Decisions API's probabilities dropped exactly where the model was unsure (see section 7), which is what you need for routing.

The headline table hides a lot. Every request was saved as one JSON line (file, ground truth, prediction, confidence, milliseconds, token counts, cost), so I went back to the 360 raw records of runs 1–3 and computed the breakdowns below. Nothing in the following subsections required new API calls.

Accuracy in detail: by class, difficulty and language

All three methods got the document type right in all 360 requests, so accuracy per class, per difficulty level and per language is 100% everywhere. The interesting signal is in how sure the Decisions API was. The table shows the mean confidence of the winning label per class (default / low resolution), next to Flash-Lite's self-reported value:

The ordering makes sense. The two least certain classes are invoice and receipt, exactly the money documents that look alike (amounts, line items, a company header) and differ mainly in one sentence about due date or payment received. Meeting minutes, leave requests and CVs, which have very distinctive layouts, sit at 0.999. Flash-Lite's numbers, by contrast, are 0.98, 0.99 or 1.00 for every document; its least confident class is still above 0.99 on average, so it does not rank the hard cases in any useful way.

The six documents with the lowest Decisions confidence (default resolution) were: doc_20 (invoice, title removed, Vietnamese, 0.9396), doc_02 (receipt, low resolution, Vietnamese, 0.9667), doc_40 (invoice, phone photo, Japanese, 0.9692), doc_28 (invoice, clean, Vietnamese, 0.9713), doc_29 (receipt, photo, English, 0.9788) and doc_15 (receipt, clean, Vietnamese, 0.9809). All six are invoices or receipts. By difficulty, the mean confidence was lowest for notitle (0.9862), then photo (0.9894), lowres (0.9923) and normal (0.9947). By language, Vietnamese documents averaged 0.9886, Japanese 0.9897 and English 0.9952. None of these dips was large enough to cause an error, but they point at where errors would appear first on a harder dataset: untitled Vietnamese money documents.

One result surprised me: low resolution gave higher type confidence than the default on average (for example invoice 0.9911 vs 0.9748, and doc_20 rose from 0.9396 to 0.9761). I do not have an explanation I can prove; it suggests that for layout-level questions, fewer image tokens do not lose the information that matters, and may even reduce distraction. I would not generalise it beyond this dataset.

Run-to-run stability: identical to the last decimal

"Stable across runs: 100%" in the main table only means each document got the same label three times. The raw data shows something stronger. For both Decisions variants, every one of the 40 documents returned exactly the same type confidence, the same signature confidence and the same token count in all three runs, down to the last floating-point digit (maximum spread across runs: 0.0). For example, doc_01 scored 0.9996314228109111 every time.

Flash-Lite, even at temperature=0, kept its labels and its signature answers stable, but its self-reported confidence changed between runs for 9 of 40 documents (e.g. doc_02: 0.99, 0.98, 0.99). That is a small thing, but it matters for audit trails and regression tests: with the Decisions API, a changed score after a prompt or taxonomy edit is caused by your edit, not by sampling noise. On a test set you can treat any difference as a real change.

Processing speed: the full latency distribution

Median and p95 do not tell the whole story, so here is the full distribution over the 120 requests per method (milliseconds, measured around the API call only):

Four observations, all from the raw records:

  1. Flash-Lite never answered in under one second; the Decisions API did 76% of the time (79% with low resolution). Flash-Lite's fastest request (1.08 s) was slower than the Decisions API's p90.
  2. Decisions latency tracks file size, not token count. The 12 slowest default-resolution requests were all phone-photo PNGs. Those files are 1.17–1.39 MB, while the other PNGs are 35–107 KB, yet all PNGs cost almost the same number of tokens (1,355–1,393). Median latency for photos was 1,519 ms against 680 ms for everything else. My interpretation is that uploading the base64 payload from a home connection dominates; downscaling or compressing images before sending is a cheap way to cut latency.
  3. The low-resolution run had two extreme outliers that the p95 hides: doc_01.png took 59.4 s in run 1 and 79.0 s in run 2 (single calls, not retries). In run 3 the same file took normal time and that run's maximum was 1.95 s. I cannot tell from my data whether this was network or server side, but it is the reason the mean latency of method B (1,920 ms) is far above its median (694 ms). In production I would set a client timeout of a few seconds and retry, rather than wait.
  4. Flash-Lite varied a lot between runs. Its median was 6.83 s in run 1, 3.42 s in run 2 and 2.68 s in run 3. The Decisions API's medians were 854, 673 and 686 ms in the same three runs. The summed request time to classify 40 documents sequentially (excluding any rate-limit waits) was 35–40 s for the Decisions API in every run, against 121–231 s for Flash-Lite. For anything interactive, predictability is worth as much as the median.

Where the tokens and the dollars go

Three details are worth knowing before you budget:

  • resolution: "low" only affected the 32 PNGs, which dropped from about 1,383 to exactly 557 tokens each (−60%). My script applies the setting only to image blocks, so the 8 PDFs cost 865 tokens in both runs. The whole 2× saving of method B comes from images.
  • Token counts are almost identical across the two APIs. Flash-Lite actually used slightly fewer input tokens per document. The Decisions API is cheaper because its input price is one third of Flash-Lite's and because there is no output to pay for, not because it reads less.
  • Output is only 18.8% of Flash-Lite's bill here. Even if Flash-Lite's 32 output tokens were free, its input alone would cost about $0.35 per 1,000 documents, still about 2.7× the Decisions API. Flash-Lite did not use thinking tokens in any request, so this baseline is already the cheapest form of text generation; a thinking model would widen the gap.

The whole benchmark (360 requests in runs 1–3) would have cost about $0.074 at list price. I ran it on the free tier.

Cost projection at 1,000, 100,000 and 1,000,000 documents

The projection uses the measured average tokens per document from this dataset (80% single-page PNG, 20% single-page PDF) and the list prices above:

cost(N) = N × (avg_input_tokens × input_price + avg_output_tokens × output_price) / 1,000,000

A. Decisions API         : N × (1,279.5 × $0.10 + 0    × $0.00) / 1e6 = N × $0.000128
B. Decisions API, low res: N × (  618.6 × $0.10 + 0    × $0.00) / 1e6 = N × $0.0000619
C. Flash-Lite + JSON     : N × (1,162.1 × $0.30 + 32.2 × $2.50) / 1e6 = N × $0.000429

Honest reading: for one team the absolute amounts are small either way. At 100,000 documents a month, the difference is about $30. The cost argument becomes real at platform scale, or when classification runs on every message or upload as a gate in front of other models. These are projections, not measurements: multi-page documents will use more tokens per document, and prices can change, so recompute with your own token counts.

Confidence-threshold routing for the document type

The routing chart above plots this, but the exact numbers are easier to use when choosing a threshold. "Automated" means the confidence of the chosen label was at or above the threshold, so the item would be filed without a person looking at it:

Because there were no type errors, this table cannot show the API catching mistakes; it only shows how the review queue would grow as you tighten the threshold. Two practical points still come out of it. First, the Decisions API degrades gracefully: each step of the threshold sends a few more of the hardest documents (the untitled invoices and receipts) to review. Flash-Lite's values sit in three buckets, so its "automation curve" jumps from 99% to 56% in one step, dropping about half of all documents at once with no ranking among them. Second, on this data a threshold of 0.9 automates everything with zero errors, and 0.95–0.97 would route only the 1–3 most ambiguous items. I would start at 0.95 and adjust after looking at real reviews. The signature question, where the API was wrong, is the real test of routing; that is next.

7. Where it breaks: the signature question

The most interesting result was not the headline number. On the yes/no question "Is there a handwritten signature on the signature line?", the Decisions API reached only 80.0%, while Flash-Lite reached 100.0%.

Looking at all 3 runs, every miss (24 at default resolution, 18 at low) was a signed document that the API called unsigned, with confidence between 0.52 and 0.65. The API was not confidently wrong; it was close to a coin flip and said so. It was hesitant on this question in general: even among its correct signature answers, 81% had confidence below 0.9. My synthetic "signature" is a thin blue scribble that takes up a tiny area of the page, a small visual detail that the default image resolution may blur away. Two lessons:

  1. Always route on confidence. With a 0.9 threshold, none of the signature errors would have been automated. But most signature checks would also have gone to a person, so for this question the API is a safe filter, not an automation. Text generation got it right here, but gives no signal for the cases where it would not.
  2. Small visual details need care. For checks like stamps, signatures or tiny check marks, test higher resolution values or crop the region first. Do not assume the type-level accuracy carries over.

Signature confusion matrix

Of the 40 documents, 24 are signed and 16 are not, so each method made 72 "signed" and 48 "unsigned" judgements over three runs:

The errors are one-sided: the Decisions API never claimed a signature that was not there. On unsigned documents it was right every time and fairly sure (confidence 0.87–0.94 at default resolution, 0.90–0.95 at low). On signed documents its confidence averaged only 0.66. In other words, a clear "no" from this API was trustworthy; a "yes" or a weak "no" was not.

Failure-case walkthrough

The 24 default-resolution misses come from just 8 documents, each missed in all three runs (the API is deterministic, so a miss repeats):

Patterns I can see, with the caveat that 8 documents is a small sample:

  • PDFs were hit hardest. 3 of the 5 signed PDFs were missed, against 5 of 19 signed PNGs.
  • Vietnamese documents were missed most often (5 of 10 signed), English 3 of 11, and Japanese 0 of 3. With only 3 signed Japanese documents, I would not read much into the last number.
  • Photo degradation was not the main cause. Only one of the 8 is a phone photo, and two (doc_05, doc_26) are clean renders with a title.
  • Lower resolution helped, not hurt. It fixed doc_05 and doc_27 and broke nothing. That contradicts the simple story "the scribble is too small, so more pixels will fix it", which I suggested above. More resolution might still help, but I did not test a higher setting, so I treat it as an open question rather than a fix.

doc_05 is a good example of a knife-edge case. In the benchmark at default resolution the API said "no" with confidence 0.596 (so about 0.40 for "yes"). At low resolution it said "yes" at 0.609. In the quickstart, with slightly different question wording, an added text part and a different option list, it said "yes" at 0.60. Three small changes to the setup moved the answer across the 0.5 line. A text-generation model would have printed a confident true or false in every case and hidden this fragility completely.

Threshold sweep for the signature question

This is where confidence routing earns its keep, because here there are real errors to catch:

At a threshold of 0.70, the default-resolution API would have handled 62.5% of signature checks on its own with zero errors: all 48 unsigned answers plus 27 of the 72 signed ones. Everything it got wrong would have gone to a person. That is a much better story than "80% accuracy", and it is only possible because the confidence carries information. With Flash-Lite I would have had to choose between trusting every answer or reviewing every answer, since it gives no per-item signal on this question at all.

Is 0.5 even the right cut-off?

The benchmark turns the yes/no probability into an answer with noul ≥ 0.5. From the recorded predictions and confidences I can recover the probability of "yes" for every request (confidence when the answer was yes, one minus confidence when it was no; this matches the quickstart output, where noul and confidence were the same 0.60 for a "yes"). The two groups separate cleanly:

  • Default resolution: unsigned documents had P(yes) between 0.06 and 0.13; signed documents between 0.35 and 0.86.
  • Low resolution: unsigned 0.05–0.10; signed 0.39–0.92.

So any cut-off between roughly 0.15 and 0.30 would have scored 100% on this dataset for both variants. The API was not blind to the signatures; it was under-confident about them, and its probabilities were systematically shifted toward "no". I want to be careful here: I picked that range after seeing the answers on the same 40 documents, which is exactly how you overfit. The right way to use this finding is to calibrate the cut-off on one labelled set and confirm it on another. But it shows a real advantage of getting probabilities instead of text: you can tune the decision rule for your own data without touching the prompt or the model.

8. Limitations and threats to validity

I would rather list the weaknesses of this test myself than have a reader find them:

  • Ceiling effect on accuracy. Both approaches scored 100% on document type, so this dataset cannot say which is more accurate on harder material. It only shows that neither is worse on a typical set of 8 office document types.
  • Synthetic, single-page documents. They were rendered from templates, have clean structure even when degraded, and the "signature" is one generated scribble style. Real scans have stamps, handwriting, multiple pages and mixed content.
  • Small sample. 40 documents, 5 per class, 24 signed. Per-language and per-format observations rest on a handful of files.
  • One baseline. I compared against Gemini 3.5 Flash-Lite only. Stronger text models (3.8 Flash, 3.6 Flash) did not return within 60 seconds on images in my environment, so I have no numbers for them. A stronger generative model might do better on hard cases, at higher cost and latency.
  • Environment. Latency was measured from a home network in Vietnam, sequentially, on free-tier keys, over a short period. The run-to-run swings in Flash-Lite and the two long outliers in method B show that conditions changed during testing. Absolute milliseconds will differ for you; the relative gap is the more transferable result.
  • Prices are list prices from the pricing page on 20 November 2026, applied to the token counts the APIs reported. I did not see an actual invoice because I ran on the free tier.
  • Prompt parity. Both methods received the same label descriptions and question wording, but the Decisions API receives them as structured fields and Flash-Lite as a prompt. That is the fair comparison of how each would be used, but it is not identical input.
  • Beta API. The model and SDK are v1beta. Behaviour, limits and pricing may change before general availability.

9. My take: which use cases it is most convenient and effective for, and when not to use it

Use the Decisions API when

  • The answer is a closed set you can write down in advance: document type, ticket category, sentiment, policy pass/fail, "which tool should the agent call", "which model should handle this request".
  • You need it inside a hot path: routing a chat message before the expensive model runs, gating an upload, pre-labelling items in a queue. About 1 second and a fraction of a cent per document is cheap enough to run on everything.
  • You want several judgements over the same input. Twenty yes/no checks on one contract cost almost the same as one, because the input is billed once.
  • You need a calibrated "I'm not sure" to decide what a human should look at.

Stay with text generation when

  • You need to extract values (invoice number, amount, dates) or explain why. The Decisions API returns no text at all.
  • The label set is open-ended or changes per request in ways you cannot enumerate.
  • The decision depends on a tiny visual detail and you have not validated resolution or cropping yet (see section 7).
  • Someone needs a written justification for each decision (an auditor, a customer, a regulator). Probabilities show how sure the model was, not what it looked at.
  • The decision is high-stakes and final with no human in the loop, such as rejecting a loan or a job application. A confident probability is still a model output, and my signature results show it can be systematically biased.
  • Volume is tiny. If you classify twenty files a week, the speed and cost advantages are worth less than the simplicity of using the chat model you already have.

Concrete scenarios, ranked by how well I think it fits

This ranking is my opinion, based on the measured properties (sub-second median, about $0.13 per 1,000 single-page documents, deterministic and informative probabilities, no text output) and on the weak spot I found (small visual details):

The common thread of the top of the list: high volume, a closed answer set, a decision that is made before something more expensive happens, and a business process that already has a "send to a person" path for the uncertain cases. Where all four are true, I think the Decisions API is the most convenient option available today, because it removes the parsing code, cuts the cost by roughly 3–7× and gives you the uncertainty signal for free. Where only one or two are true, it is a nice-to-have.

A quick checklist before choosing it

  1. Can I write every possible answer down before the request? If not, use text generation.
  2. Do I need any text back (values, reasons, summaries)? If yes, use the Decisions API only as the first stage.
  3. Is there a review path for low-confidence items? If not, build one before going live.
  4. Have I measured accuracy per question on at least a few dozen labelled examples of my own? My results show that one strong question (document type) and one weak question (signature) can sit in the same request.
  5. Have I chosen thresholds from data, and confirmed them on a second set?

The pattern I would actually ship is a two-stage pipeline: the Decisions API classifies and scores everything cheaply, high-confidence items go straight through, and only low-confidence items or ones needing extraction go to a generative model or a human. It is still v1beta, Vertex AI support is "coming soon", and the Playground needs billing, so for production I would wait for GA or keep a fallback path.

On standardisation

Typed question → probabilities is a cleaner contract than "prompt → text → regex", and I expect other providers to converge on it. Today it is Gemini-specific, so I keep the question definitions (labels + descriptions) in one config file that both the Decisions call and the text-generation fallback read. Switching providers then means changing the call, not the taxonomy.

10. How I will apply the Decisions API to streamline my daily work

I work at a software development company, writing technical content, preparing demos and supporting project teams. Concretely:

None of these need generated text, all of them run many times a day, and all of them benefit from knowing when the model is unsure. That is exactly the shape of problem this API is built for.

Workflow 1: an inbound file sorter

This is the first thing I will build, because it is almost the benchmark itself. Files that customers send (specifications, quotations, contracts, screenshots) currently arrive through email and chat and get saved by hand. The sketch:

new file in shared "inbox" folder
        │
        ▼
 downscale image / keep PDF as is      (smaller upload = lower latency, see section 6)
        │
        ▼
 Decisions API: one request
   doc_type      : choice  (spec | quotation | contract | invoice | bug_screenshot | other)
   needs_action  : noul    ("Does this file ask us to reply, sign or pay?")
        │
        ├── doc_type confidence ≥ 0.95 and choice ≠ "other"
        │        └─► move to /project/<doc_type>/ and log label + probabilities
        │
        └── otherwise
                 └─► move to /check-me/ with the top-2 labels in the file note
 needs_action ≥ cut-off ──► post a message to the project channel

Three design decisions come straight from the results. The type threshold starts at 0.95, where only the 1–3 most ambiguous items in my test would have gone to review. The yes/no question is used only to notify, never to delete or approve anything, because section 7 showed yes/no questions can be biased. And every decision is logged with its probabilities, so after a few weeks I can recompute the automation and error rates on real data instead of synthetic documents.

Workflow 2: a pre-submission check for my own posts

Every quest post I write has to answer specific requirements, and I check them by rereading. With the Decisions API the check becomes one request over the draft text, with one noul per requirement plus a score for overall depth. A sketch of the question set, reusing the same call pattern as the benchmark:

questions = {

Workflow 3: a cheap router in internal AI tools

Internal chat tools tend to send every question to the strongest model available. A single choice question in front of it ("simple FAQ / needs reasoning / needs code / out of scope") lets simple questions go to a small model or a fixed answer and keeps the expensive model for the requests that need it. The router's own cost is input-only, and in my test the Decisions API returned in under a second three times out of four, so the user should barely notice the extra hop. An "out of scope" option with a confidence threshold doubles as a guardrail.

Rollout plan

  1. Shadow mode (2 weeks). Run the sorter on copies of incoming files and log its answers, while files are still sorted by hand. Compare the two.
  2. Calibrate. From the log, pick the type threshold and the yes/no cut-off that give zero automated errors, then confirm them on the following week's files.
  3. Automate the confident part. Turn on automatic moves above the threshold; everything else keeps going to the review folder.
  4. Review monthly. Track three numbers: share automated, errors found among automated items, and time spent on the review folder. Add or rename classes only through the shared config file, then re-run the labelled set.
  5. Keep the fallback. Until the API is generally available, keep a text-generation path that reads the same label config, so an outage or API change does not stop the workflow.

What I expect it to save (estimates, not measurements)

I have not run these workflows on real work yet, so the following is an estimate with the assumptions written out. Suppose a project receives 50 files a week and sorting one by hand (open, decide, rename, move) takes about 30 seconds. That is roughly 25 minutes a week. If the confident share on real files is similar to the 0.95 threshold row in my test, most of those files would be sorted automatically and only a few would need a look, so I would expect to get back most of that time, plus fewer misfiled documents. The API cost at that volume is a fraction of a cent per week and does not matter. The larger, harder-to-quantify gain is consistency: the same file always gets the same label, and every label comes with a number that says how much to trust it. I will report the real numbers after the shadow-mode period rather than claim them now.

11. FAQ

Is the Decisions API more accurate than a generative model?

On document type in my test, neither was more accurate: both were 100%. On the signature question, Flash-Lite was more accurate at the default 0.5 cut-off (100% vs 80%), but the Decisions API's probabilities would have separated signed and unsigned documents perfectly with a different cut-off. Accuracy depends on the question, so measure it per question.

Why is it faster?

It does not generate an answer token by token; it scores the options you provide. In my test that meant a 754 ms median against 3.34 s, and a much narrower spread. The remaining time was dominated by input size: large photo files were the slowest requests.

Should I always use resolution: "low"?

For layout-level questions on my dataset, yes: it halved the cost, kept type accuracy at 100% and even improved signature accuracy from 80% to 85%. But it only applies to image inputs, and I tested only one dataset. Run your own labelled set at both settings before switching.

Can I trust the confidence values?

More than a self-reported confidence. In my data they were lowest on the genuinely confusable classes and on the signature errors, and identical across runs. They were not perfectly calibrated: signed documents got systematically low "yes" probabilities. Treat them as a ranking you can threshold, and choose the threshold from your own labelled data.

Can it read the invoice number or the total for me?

No. It returns probabilities, never text. A score question can bucket an amount into ranges (the quickstart put a quotation in "10–50 million VND" at 0.97), but extracting the exact value needs a generative model or an OCR/extraction service.

Is it ready for production?

Functionally it was solid: all 240 Decisions requests in runs 1–3 returned a valid, typed answer (the script retries on errors such as rate limits, and I did not log how many retries happened). But it is v1beta, Vertex AI support was still "coming soon", and I saw two very slow calls in one run. I would use it in production behind a timeout, a retry and a fallback path, and start with workflows where a wrong answer is cheap to fix.

12. Conclusion

  • On 40 multilingual, partly degraded business documents, the Decisions API matched a JSON-mode text-generation baseline on document-type accuracy while being about 4× faster and 3.4–6.9× cheaper.
  • Its real advantage is the probability output: it lets you automate the confident cases and route the rest, which a self-reported "confidence" field from a generative model does not.
  • It is not magic for small visual details. The signature check showed hesitant answers that must go to review, or be fixed with resolution or cropping.
  • Treat it as the first stage of a pipeline: classify, score and route, and keep text generation for extraction and explanation.
  • Its answers were bit-for-bit identical across runs, which makes thresholds, tests and audits reproducible. Flash-Lite's labels were stable, but its self-reported confidence was not.
  • At the measured token counts, classifying 1,000,000 single-page documents would cost about $128 (or $62 at low resolution) against about $429 with Flash-Lite. The real value at small scale is speed, simplicity and the confidence signal, not the bill.
  • For my own work, I will start with an inbound file sorter in shadow mode, then a requirement checker for drafts and a router for internal AI tools, and only automate what the logged probabilities show is safe.
