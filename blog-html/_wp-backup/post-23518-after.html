I wrote two Agent Skills once, put them in a single folder, and ran the same tasks through Claude Code and OpenAI Codex CLI. Here is what transferred, what did not, and the full skills so you can try them yourself.

This post is written to answer three concrete questions, and each one has its own section so you can jump straight to it:

  • Requirement 1 – create a common Agent Skill that follows the open specification (agentskills.io) and the Claude Code skills documentation and works in both Claude Code and Codex: sections 2 to 4 (format, one shared folder, full source of both skills).
  • Requirement 2 – test the skill with requirement definition and code review and document the results objectively: sections 5 to 7 (setup, video, results with tables taken from the real output files), plus section 10 on the limits of the test.
  • Requirement 3 – my own opinion on standardisation and how I will use skills in daily work: sections 11 and 12, followed by an FAQ and a short conclusion.

1. Why a common skill matters

Agent Skills are folders of instructions (a SKILL.md plus optional references and scripts) that a coding agent loads only when a task needs them. Our team, like many, does not use a single agent: some people prefer Claude Code, others Codex, and reviewers use GitHub Copilot. If every tool needs its own prompt files, our review checklist and our requirements template slowly drift apart.

Anthropic donated the Agent Skills specification to the Agentic AI Foundation in October 2026, and Codex and GitHub Copilot both read the same format. The question for this quest is practical: can I write a requirement-definition procedure and a code-review procedure once, and get the same behaviour from Claude Code and Codex?

I picked these two procedures on purpose. Requirement definition is a generative task: the agent has to turn vague text into a structured document, and there is no single right answer. Code review is an analytical task: there is a ground truth (the bugs that are really in the file), so detection can be counted. If one skill format carries both kinds of work across two agents, it is a good sign that it can carry most of the procedures a development team writes down.

2.1 What each frontmatter field is for (and how I filled it)

  • name: the identifier you type after / in Claude Code or $ in Codex. Because it must equal the folder name, renaming a skill means renaming the folder; the validator catches a mismatch. I used requirement-definition and code-review, which read naturally in both invocation styles.
  • description: the only text an agent sees about a skill before deciding to load it. I wrote it in two halves: one sentence on what the skill produces, then a "Use when…" sentence listing the words people actually type ("PR review", "bug hunt", "acceptance criteria", "spec").
  • license: MIT, so that the skills can be copied between repositories without a legal question.
  • compatibility: free text about the environment. I used it to record which tools the skill was tested with and what access it needs ("Read-only; does not modify code" for the review skill). Agents do not enforce this field; it is documentation for the next person.
  • metadata: an open key/value map. I put author and version there. The version is a quoted string ("1.0") so YAML does not turn it into a number.
  • allowed-tools: deliberately not used. It is marked experimental in the specification, and I did not want the test to depend on a field the two tools might interpret differently. Permissions were set on the command line instead (section 5).

Claude Code also understands some extra frontmatter fields of its own, described in its skills documentation. I avoided all of them: anything outside the open specification is, by definition, not guaranteed to mean the same thing in Codex.

2.2 How a skill is discovered and loaded

Both tools follow the same three-step pattern that the specification calls progressive disclosure:

  1. Discovery. At start-up the agent scans its skill folders and keeps only the name and description of each skill in context. This is cheap, so a repository can hold many skills.
  2. Activation. When the user invokes a skill explicitly, or a request matches a description, the body of SKILL.md is loaded.
  3. On-demand resources. Files under references/, scripts/ or assets/ are read only when the instructions point to them.

The Codex logs from my runs show this pattern directly. In the discovery run, Codex answered "based on the skills configuration provided in your prompt", i.e. the names and descriptions were already in its context without opening any file. In the task runs, the SKILL.md body never appears as a shell command, but the reference files do: Codex ran cat .agents/skills/requirement-definition/references/template.md and cat .agents/skills/code-review/references/checklist.md at the point where the procedure tells it to use them. Claude Code in print mode only shows its final answer, so I cannot show its file reads, but both requirement documents reproduce column headers that exist only in template.md (for example "Category (Security/Audit/Performance/Usability)"), so both agents clearly read the reference file.

3. Requirement 1: one common skill folder for two agents

To avoid two copies drifting apart, I keep the real files in .agents/skills/ (read by Codex and Copilot) and make .claude/skills a directory junction pointing to it (a symlink works the same on macOS/Linux):

demo-project/
├── .agents/skills/
│   ├── requirement-definition/
│   │   ├── SKILL.md
│   │   └── references/template.md
│   └── code-review/

I used only fields from the open spec (name, description, license, compatibility, metadata) and no tool-specific extensions, then validated both skills with the reference validator:

pip install skills-ref
agentskills validate .agents/skills/code-review              # Valid skill
agentskills validate .agents/skills/requirement-definition   # Valid skill

3.1 Design decisions that keep a skill portable

Passing the validator only proves the file is well-formed. Whether it behaves the same in two agents depends on how the instructions are written. These are the choices I made, and why:

  • Describe actions, not tool names. The requirement skill says "search for nouns from the request", not "use the Grep tool". Claude Code and Codex expose different tools (Codex on Windows runs everything through PowerShell), so naming a specific tool would make the instructions wrong in one of them.
  • Fix the output shape, leave the thinking free. Both skills prescribe an exact output (a template with nine headings, a five-column review table, a fixed severity scale and verdict rule). That is what makes two outputs comparable. How the agent finds problems is left to the model.
  • Put long content in references/. The template and the checklist live in separate files linked with relative Markdown links. Each SKILL.md stays short (29 and 44 lines).
  • No scripts. A scripts/ folder would have needed Python or a shell that behaves the same on both sides. For procedures that are mostly judgement, plain Markdown is the most portable choice.
  • Testable rules. Every rule in the skills can be checked by reading the output ("each AC references an FR", "any Critical or Major → REQUEST CHANGES"). That made the evaluation in section 7 a matter of counting, not taste.

4. The two skills (full source)

Copy these four files into .agents/skills/ in your repository (and link .claude/skills to it) to try them yourself. They are MIT-licensed.

4.1 requirement-definition/SKILL.md

---
name: requirement-definition
description: Turn an informal feature request (Slack message, email, meeting note) into a structured requirements document with user stories, numbered functional and non-functional requirements, Given/When/Then acceptance criteria, assumptions and open questions. Use when the user asks to define, clarify, write or review requirements, a spec, or acceptance criteria for a feature.
license: MIT
compatibility: Agent Skills standard (agentskills.io). Tested with Claude Code and OpenAI Codex CLI. Needs read/write access to the repository.
metadata:
  author: phatlt
  version: "1.0"
---

# Requirement definition

Produce a requirements document that a developer, a tester and the requester can all agree on.

## Procedure

1. **Read the request and the code it touches.** Find the related modules (search for nouns from the request) so requirements match the real data model. Never invent tables or fields that do not exist without marking them as *new*.
2. **Separate facts from guesses.** Anything the requester did not state explicitly goes to *Assumptions* (A-xx). Anything that blocks implementation goes to *Open questions* (Q-xx) addressed to a named role.
3. **Write the document** using exactly the template in [references/template.md](references/template.md). Keep every heading, in the same order, even if a section is "None".
4. **Number everything**: FR-01, NFR-01, AC-01, A-01, Q-01. Each acceptance criterion references the FR it verifies.
5. **Acceptance criteria** use Given / When / Then and must be testable (concrete values, no "should work well").
6. **Save** the document to `docs/requirements/<kebab-case-feature-name>.md` and print a 3-line summary: number of FRs, NFRs, ACs and open questions.

## Rules

- Write in the language of the request unless the user asks otherwise.
- Prefer short sentences; one requirement per line.
- Flag security, privacy and audit needs explicitly as NFRs.
- Do not write implementation code in this skill.

4.3 code-review/SKILL.md

---
name: code-review
description: Review source code or a diff for security, correctness, error handling, maintainability and test coverage, and report findings in a fixed severity-ranked format with file:line references and concrete fixes. Use when the user asks for a code review, PR review, bug hunt, security check or "look over this code".
license: MIT
compatibility: Agent Skills standard (agentskills.io). Tested with Claude Code and OpenAI Codex CLI. Read-only; does not modify code.
metadata:
  author: phatlt
  version: "1.0"
---

# Code review

Review like a senior engineer who must sign off the change. Be specific, cite lines, propose fixes. Do not edit the code.

## Procedure

1. **Scope**: review the files or diff the user names. If none are named, review files changed in the working tree (`git diff --name-only`), otherwise all source files in the current directory.
2. **Read every line** of the in-scope files. Check each item of [references/checklist.md](references/checklist.md).
3. **Classify** every finding with exactly one severity:
   - **Critical**: security hole, data loss, secret exposure. Must fix before merge.
   - **Major**: wrong behaviour, broken business rule, crash risk.
   - **Minor**: error handling, robustness, maintainability.
   - **Nit**: style, naming, comments.
4. **Report** using the output format below, sorted Critical → Nit. One finding per row. Merge duplicates.
5. Finish with a one-line **verdict**: `APPROVE`, `APPROVE WITH COMMENTS` or `REQUEST CHANGES` (any Critical or Major → REQUEST CHANGES).

## Output format

## Code review: <scope>

| # | Severity | Location | Finding | Suggested fix |
|---|----------|----------|---------|---------------|
| 1 | Critical | file.py:12 | ... | ... |

**Summary:** <n> Critical, <n> Major, <n> Minor, <n> Nit
**Verdict:** REQUEST CHANGES

## Rules

- Location must be `path:line` (or `path:start-end`).
- Never report something you did not verify in the code.
- If tests are missing for changed logic, report it as Minor.

4.4 code-review/references/checklist.md

# Review checklist

## Security
- [ ] No secrets, tokens or passwords in source code or logs
- [ ] All SQL uses parameter binding (no string formatting / f-strings)
- [ ] Authorization: the caller is allowed to perform the action (e.g. no self-approval)
- [ ] Input validation for user-supplied values

## Correctness
- [ ] Logic matches docstrings, comments and business rules (inclusive/exclusive ranges, off-by-one)
- [ ] State transitions are checked (e.g. cannot approve something already approved or cancelled)
- [ ] No mutable default arguments or shared global state

## Error handling & resources
- [ ] No silent `except: pass` / swallowed exceptions
- [ ] Connections, files and cursors are closed (context managers)

## Maintainability & tests
- [ ] Functions are small and named for what they do
- [ ] Changed logic has tests

5. Test setup

Inputs (identical for both tools)

  • Requirement definition: a real-style, messy Slack message from HR asking for "self-service leave cancellation", with partial cancellation, manager notification and audit hints buried in casual text.
  • Code review: a 50-line Python module for leave requests (fictional) with 6 seeded issues: a hard-coded admin token, SQL injection through an f-string, an off-by-one day count that contradicts its docstring, a mutable default argument, a missing authorization and state check in approve_request, and a silent except Exception: pass.

This is the complete feature request both agents received, exactly as stored in feature-request.txt:

From: HR team (Slack message, pasted as-is)

hi dev team! employees keep asking us to cancel leave they already submitted, sometimes even after it's approved :(
can we let them cancel by themselves in the app? managers should get notified. also if the leave already started they shouldn't be able to cancel the whole thing i think?? maybe only the remaining days.
we also want to see who cancelled what for audit. need this before the year-end holidays if possible. thanks!!

The same leave_service.py file served two purposes: it was the code under review, and it was the "existing code" the requirement skill had to read so that its requirements matched the real data model (a leave_requests table with employee, start, end, days, reason, status and approver).

Commands (exactly what was run)

# Claude Code
claude -p "/requirement-definition feature-request.txt (answer in English)" --permission-mode acceptEdits
claude -p "/code-review leave_service.py (answer in English)" --allowedTools Read,Grep,Glob

# Codex CLI
codex exec --skip-git-repo-check --dangerously-bypass-approvals-and-sandbox "$requirement-definition feature-request.txt (answer in English)"
codex exec --skip-git-repo-check --dangerously-bypass-approvals-and-sandbox "$code-review leave_service.py (answer in English)"

Environment, stated plainly: Windows 11, Claude Code 2.1.329 (its default model) and Codex CLI 0.171.0. I did not have a ChatGPT/OpenAI subscription for Codex, so I configured Codex with a custom model provider: Gemini 3.5 Flash-Lite, reached through a small local bridge that exposes the OpenAI Responses API. Skill discovery, loading, tool calls and file edits are all done by Codex itself; only the model behind it differs. That matters for the results: differences in depth below are mostly model differences, while differences in procedure are what the skill controls.

How I scored the results

To keep the evaluation objective, I decided the scoring rules before looking at the outputs:

  • Procedure compliance is checked rule by rule against the text of each SKILL.md: does the output have the nine template headings in order, numbered IDs, ACs that cite an FR, the review table columns, the severity scale, the verdict rule, and so on. A rule is either followed, partly followed or not followed.
  • Code review detection is checked against a ground-truth list of the six seeded issues (file, line, expected severity) that I wrote before the runs and never showed to the agents. A seeded issue counts as found if a finding describes the same defect at the same code, whatever severity it was given. Severity is then compared separately.
  • Timing is the wall-clock time of each command as captured by the terminal recorder used for the video. Token counts are only available for Codex, which prints them at the end of a run.
  • Every number in section 7 comes from the saved output files of the runs shown in the video; nothing was re-run or edited for the comparison.

7. Requirement 2: test results on both platforms

7.1 Discovery: both agents found the same skills

Asked "which skills can you use?", Claude Code listed code-review and requirement-definition from .claude/skills (through the junction). Codex listed the same two from .agents/skills, next to its four built-in system skills. Neither tool needed any change to the files.

Two details from the logs are worth noting. Claude Code answered in 10.7 seconds and even explained that .claude/skills is a link to .agents/skills. The Codex discovery run took 67.1 seconds and used 19,451 tokens, mostly because the model first tried three shell commands (Get-ChildItem, git status, ls) that the read-only sandbox rejected, and then answered from the skill list already in its prompt. Both descriptions came back almost word for word, for example Codex's "Review source code or a diff for security, correctness, error handling, maintainability, and test coverage", which is the first half of my description field.

7.2 Requirement definition

The procedure transferred completely: same headings, same numbering scheme, same file location. The depth did not: Claude Code's document read like a spec I could hand to a tester (for example "Today is 2026-12-23; #11 is approved 2026-12-22 to 2026-12-26; cancel from 2026-12-24 → end = 2026-12-23, days = 2"), while the Codex run with a Flash-Lite model produced a correct but thin skeleton.

Both agents understood the business rule the same way, and both wrote a Given/When/Then with concrete dates. The difference is precision. Claude Code turned the ambiguity into an explicit decision (A-02: "Remaining days means days from tomorrow onward"), a separate negative test (AC-05 rejects a cancel-from date of today) and exact day counts. Codex's AC says "days are recalculated" without the expected number, so a tester would still have to work it out.

Step 1 of the skill ("read the code it touches") produced the largest gap. Claude Code's requirement run noticed four things in leave_service.py that affect the feature: there is no cancelled status, audit table or notification module yet (marked new); there is no manager field for pending requests, only approver (Q-03); leave_days returns one day less than its docstring says, which would make cancelled-day counts wrong (A-07, Q-07); and the existing SQL is string-formatted, so NFR-02 requires parameterised queries for the new feature. Codex's log shows it read the same file, but its document only reflects it in A-02 ("schema will require new columns/tables"). Its AC-01 uses a cancelled status without marking it as new.

Rule-by-rule compliance of the requirement-definition skill

What the Codex requirement run actually did

Because Codex prints every shell command, its log shows the procedure being executed step by step. In order, it ran git status, read feature-request.txt, listed the project files (with two failed attempts using Unix syntax, find and ls -la, before Get-ChildItem worked), read leave_service.py, read template.md, created the folder (a failed mkdir -p, then New-Item), tried to write the file with a Bash heredoc (fails in PowerShell), wrote it with Set-Content, and finally ran git add on the new document (the first attempt with && failed in Windows PowerShell 5.1). That is 16 commands, 5 failures and 62,334 tokens. The order matches steps 1, 3 and 6 of the skill exactly; the failures are all about shell dialect, not about the skill.

What the Codex review run did

Codex ran four commands: git status, cat leave_service.py, cat .agents/skills/code-review/references/checklist.md and git diff leave_service.py, for 22,437 tokens in total. Reading the checklist right after the file is step 2 of the skill. The git diff comes from step 1 (scope), even though I had named the file, so it was not needed. The first git status also showed that the requirement document from the previous Codex run had been staged with git add, which is how I noticed that side effect (section 8). The code itself was not modified by either agent, as the skill requires.

7.4 Verdict: can the procedures be reused across both platforms?

My answer is yes, the procedures are reusable, with a precise meaning: the skill transfers the process and the output contract across platforms, and that part worked 100% in this test. It does not transfer quality, which follows the model you plug in.

7.5 Why the outputs differed

  • The model. Claude Code ran with its default model; Codex ran with Gemini 3.5 Flash-Lite through a bridge, and Codex itself warned "Model metadata for gemini-3.5-flash-lite not found. Defaulting to fallback metadata; this can degrade performance". A lightweight model with fallback metadata is the most likely cause of the thinner documents.
  • The shell. Codex on Windows executes through Windows PowerShell, and the model kept writing Unix commands. Five of its sixteen commands in the requirement run failed for that reason alone, which costs time but did not change the result.
  • Permissions. The Claude Code review ran with read-only tools, so it could not run git; Codex ran without a sandbox and did. In this test that only changed side effects, not findings.
  • Not the skill. Both agents received the same text and both followed it. I could not find a difference that I can trace back to the skill being read differently.

8. What I learned (including the Windows surprises)

  • Portability is real at the procedure level. One SKILL.md, unchanged, produced the same structure in both agents for both tasks. The skill reliably transfers the what and the format; the model decides the depth.
  • Write descriptions for matching, not for humans. Both agents chose the right skill from the description alone. Including trigger phrases ("PR review", "acceptance criteria") matters more than a nice summary.
  • Put the checklist in references/. Both agents opened checklist.md and template.md only when the procedure told them to, which keeps the always-loaded part small.
  • Codex on Windows: the default sandbox blocked every shell command, including reading a file, so the first runs only produced "please paste the file" answers. Options are Codex's Windows sandbox setup (machine-wide sandbox accounts, admin) or running without the sandbox. I chose the latter, only inside a throwaway demo folder.
  • Without a sandbox, agents do more than you asked. In one run Codex also executed git add on the generated document. Harmless here, but a good reminder: a skill describes a procedure, it does not restrict tools. Keep review skills on read-only permissions (Claude Code: --allowedTools Read,Grep,Glob).
  • Language settings leak in. My personal Claude Code settings ask for Vietnamese answers; the skill's "write in the language of the request" did not override that, so I added "answer in English" to both prompts for a fair comparison.

9. Portability pitfalls and a checklist for cross-tool skills

Everything in section 8 can be turned into rules. This is the checklist I now use before I commit a skill that has to work in more than one agent:

  1. Frontmatter uses only open-spec fields, and the skill passes agentskills validate. Tool-specific fields go in a separate, clearly marked variant if they are really needed.
  2. One source folder. Real files in .agents/skills; other tool folders are links. On Windows, check that the junction survives git clone on a colleague's machine; if not, generate the link in a setup script.
  3. No shell commands in the instructions unless they are cross-platform. git commands are safe. ls -la, find, mkdir -p and heredocs are not, as the Codex log shows. Prefer "create the folder if it does not exist" over a command.
  4. The description contains the words users type, both the formal ones ("acceptance criteria") and the casual ones ("look over this code").
  5. The output contract is explicit: headings, table columns, ID scheme, file path, final line. This is the part that transfers best, so it should carry as much of the process as possible.
  6. Rules are checkable by reading the output, so the same test can grade both tools.
  7. Permissions are set outside the skill: read-only tool lists for review skills, a sandbox or a throwaway branch for skills that write files.
  8. Language is stated explicitly in the prompt or the skill, because personal settings can override a "use the language of the request" rule.
  9. A regression input lives next to the skill (for example a file with seeded bugs and its ground truth), and every change to the skill is re-run against it in each tool.

10. Limitations of this test

I want the results to be read for what they are, so here are the weaknesses I am aware of:

  • One run per tool and task. Agent output varies between runs. Counts such as "17 vs 6 FRs" describe these runs, not an average.
  • Different models. Codex was not running an OpenAI model, so this is not a "Claude Code vs Codex" quality comparison. It is a test of whether the same skill drives two different agent runtimes.
  • The checklist names the bug classes. My review checklist mentions self-approval, off-by-one, mutable defaults and except: pass, which are exactly the seeded issues. That makes 6/6 easier: it shows that the agents followed the checklist, which is what I wanted to test, but it says less about finding unknown bugs.
  • A small, synthetic file. Fifty lines with obvious defects is far from a real pull request with hundreds of changed lines and context spread over many files.
  • Explicit invocation. The task runs used /skill and $skill. Automatic selection by description was only checked in the discovery step, not on the tasks themselves.
  • Self-scoring. I wrote the skills, the seeded bugs and the scoring. I reduced the bias by fixing the ground truth and the rules before the runs and by publishing the raw outputs in the video, but a second reviewer would be better.
  • Not covered: GitHub Copilot (it reads the same folder but I did not test it), macOS/Linux, non-English requests, and skills that include scripts.

11. Requirement 3: my opinion on skill standardisation

I think the Agent Skills standard is the right size: it standardises where instructions live and how they are discovered, and leaves everything else to plain Markdown. That is why one file worked unchanged across two very different agents.

What is still missing for teams:

  • One project folder. Codex reads .agents/skills, Claude Code reads .claude/skills. A junction or symlink works, but it is a trap on Windows and in some CI checkouts. Claude Code reading .agents/skills too would remove the last friction.
  • Permissions in the standard. allowed-tools is still experimental and interpreted differently. A review skill should be able to declare "read-only" portably.
  • Versioning and testing. Skills are code for agents. They need version pins and small regression tests (like the 6 seeded bugs here), otherwise a "small wording change" silently changes team behaviour.

Even so, I would standardise on it now: the cost is one folder in the repository, and the benefit is that our team process survives a change of tools.

11.1 What I see as the real benefits

  • The process becomes an artefact. Before, "how we review code" lived in people's heads and in a wiki page nobody opened. A skill is a file in the repository that is reviewed in pull requests, has a history, and is executed every time. I find that the biggest change, bigger than any time saving.
  • Freedom of tool choice without losing consistency. In my test, two agents with two different models produced reports with the same columns, scale and verdict. A team lead can let each developer use the agent they like and still get comparable output.
  • Cheap to adopt, cheap to leave. A skill is Markdown. If the standard disappeared tomorrow, the template and checklist would still be useful documents for humans.
  • Comparability makes evaluation possible. Because the output format is fixed, I could score both tools with the same table. Without that, comparing agents is a matter of impressions.

11.2 Risks and limits of standardisation

  • A standard format does not give standard quality. My results show this clearly: the same skill produced 17 functional requirements in one agent and 6 in the other. Teams should not read "we use a shared skill" as "every tool now reviews equally well".
  • Over-specification. A skill that prescribes every step can stop a strong model from doing better than the checklist. Claude Code's TOCTOU finding was not in my checklist. I prefer to fix the output and the minimum checks, and leave room for extra findings.
  • Fragmentation through extensions. Each vendor adds its own frontmatter fields. If teams start depending on them, "portable" skills quietly become single-tool skills again. I would keep tool-specific fields out of shared skills.
  • False sense of control. As the git add episode showed, a skill describes what to do; it does not prevent anything. Safety still has to come from the agent's permission settings.

11.3 Versioning and governance: how I would run shared skills

  • Version in metadata, history in git. I already put version in metadata. I would bump it on any change to the output contract (a new column, a renamed heading) because those changes break anyone who parses or compares the output.
  • Owners. Each shared skill gets an owner, and .agents/skills is covered by code-owner review, so a skill cannot change without the owner's approval.
  • Regression inputs. Every skill ships with at least one test input and an expected result, like leave_service.py and its six seeded issues. A pull request that changes the skill includes the before/after output from each supported agent.
  • One shared repository for common skills. Project-specific skills stay in each project; company-wide ones (review, requirements, release notes) live in one repository and are copied or linked into projects at a pinned version.

11.4 Security: skills are executable instructions

My two skills contain no scripts, but the specification allows a scripts/ folder, and an agent will run those scripts with whatever permissions it has. Even plain Markdown is effectively code, because the agent obeys it. In my opinion, that means a third-party skill deserves the same care as a third-party package: read it fully before installing, prefer skills from known sources, pin the version, and re-read the diff when it updates. Instructions such as "also send the file to this URL" could be hidden in a long reference file. For our team I would allow only skills from our own repository on client projects, and run any skill with scripts inside a sandbox or a disposable branch.

11.5 What I would like the specification to add

  • A stable, portable way to say "this skill is read-only" or "this skill may write only under docs/", honoured by every tool.
  • One agreed project folder that every tool reads, so no links are needed.
  • An optional, standard place for test inputs and expected outputs, so that skill authors can share evaluations along with the skill.

12. Requirement 3: how I will use Agent Skills in my daily work

The first step is cheap: add .agents/skills/ with these two skills to one active project, link .claude/skills to it, and compare a week of reviews before and after.

12.1 Workflow 1: from customer message to agreed spec

The requirement run gave me the most useful single artefact of this test: ten open questions, each addressed to a role. That is exactly the list I usually write by hand after a customer call. My new routine will be:

  1. Paste the customer's message into a text file in the project, without personal or confidential data.
  2. Run /requirement-definition on it, in whichever agent I have open.
  3. Review the Assumptions and Open questions sections first, since they are where the agent guessed; send the questions to the customer the same day.
  4. When answers arrive, update the document and move answered questions into requirements; the acceptance criteria become the tester's starting point.

12.2 Workflow 2: a consistent first pass before human review

I will not replace human review with the skill. Instead, the author of a pull request runs code-review on their own diff before asking for review and fixes the Critical and Major rows first. The human reviewer then reads the report, confirms or rejects each row, and spends their time on design questions that a checklist cannot cover. Because the format is the same in every agent, the report can be pasted into the pull request description regardless of which tool produced it.

12.3 Workflow 3: personal skills for repeated writing tasks

Outside code, I repeat the same checks every time I submit a blog post for this program: is my own opinion stated, is the daily-work application concrete, are secrets and client data hidden in screenshots and videos. A small blog-review skill with that checklist in references/ would catch omissions before submission, and it would work in whichever agent I happen to be using that day.

12.4 Rolling it out to the team

  1. Week 1: add the two skills to one active project, with the folder link and a short README line. Use them myself on every new request and every pull request I open.
  2. Week 2: ask two colleagues, one on Claude Code and one on Codex, to use the same skills, and collect the reports side by side, as in section 7.
  3. Week 3: adjust the template and checklist based on real false positives and missed issues, and bump the version.
  4. Week 4: if the team agrees, move the skills to a shared repository and add them to new projects by default.

12.5 Expected benefit (my estimates, not measurements)

I have not measured time savings in daily work yet, so these are my own expectations, to be checked during the rollout above. The measured facts are only the run times in section 7: 58 seconds for a full requirements draft and about 30 seconds for a review of this small file.

  • Requirement drafts: I expect the first draft of a spec to become mostly a review task instead of a writing task, and I would guess it saves me a large part of the time I currently spend on the first version. The bigger gain I expect is fewer forgotten questions, because the template forces the Assumptions and Open questions sections.
  • Reviews: I expect fewer review rounds for basic issues (secrets, SQL, missing tests), because authors will see them before a human does.
  • How I will check: count review rounds per pull request and the number of questions sent back to customers after the spec is "done", before and after the rollout.

One rule stays the same with or without skills: the person who runs the skill owns the result. The agent's document and review are drafts until a human has read them.

13. FAQ

Do I need two copies of each skill? No. Keep one copy in .agents/skills and make .claude/skills a link to it, as in section 3. Both tools discovered the same files this way.

Does the skill make a weaker model as good as a stronger one? No. In this test it made the weaker setup follow the same process and format, and find the same six seeded issues, but its documents and fixes were much less detailed.

Can I use Claude Code's extra frontmatter fields? You can, but then the skill is no longer guaranteed to behave the same in Codex. For shared skills I keep to the open-spec fields.

Do I have to type /skill or $skill every time? No; both tools can pick a skill from its description. I used explicit invocation in the tests so that the comparison was not affected by whether the skill was selected.

Is it safe to run Codex without the sandbox like I did? Only in a throwaway folder. On a real project, set up the Windows sandbox or run on Linux/macOS with the sandbox enabled, and keep review skills read-only.

Does it work with GitHub Copilot? Copilot's documentation says it reads .agents/skills and .claude/skills, but I did not test it here.

14. Conclusion

  • Requirement 1: I created two skills, requirement-definition and code-review, using only open-spec fields. Both pass the reference validator and were discovered unchanged by Claude Code (through .claude/skills) and Codex CLI (through .agents/skills) from a single folder.
  • Requirement 2: In both tools, both procedures were followed and the output structure was identical. Both agents found all 6 seeded issues and gave the same verdict. Depth was very different (17 vs 6 functional requirements, 13 vs 8 review findings), and I attribute that mainly to the model behind each agent. The procedures are reusable; quality is not guaranteed by the skill.
  • Requirement 3: I think the standard is worth adopting now because it turns team processes into versioned files that survive a change of tools. It still needs portable permissions, one shared folder and a habit of testing skills like code. I will start with requirement drafts and pre-review on one project, then roll the skills out to the team over a month.
